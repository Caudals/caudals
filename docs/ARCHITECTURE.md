# Caudals Architecture

## System Overview

Caudals evaluates companies' AI systems and builds custom datasets with freelance domain experts (`product-specs/overview.md`). Production includes the public marketing funnel and deployed invite-only evaluation product. Customer rollout remains subject to workspace entitlements, target readiness and the remaining release gates; see `product-specs/evals-platform-implementation-spec.md` and `evals/work-packages/WP-08.md`–`WP-15.md`.

Current production scope:

- Public marketing, authority and demand capture: `/`, `/sectors`, `/sectors/*`, `/methodology` (`/es/metodologia`), `/contact`, `/call`, `/blog`, `/blog/*`, `/newsletter`, `/newsletter/*`, `/legal/*`
- Public APIs for that funnel: `/api/contact`, `/api/newsletter`, `/api/analytics/track`, `/api/demo/*`
- Public demo: `/demo`, the public front door while `DEMO_PUBLIC=true` (launch L-04); self-serve sign-up from it at `/workspace/signup`; direct work-email sign-up at `/workspace/start` (app host, `SELF_SERVE_DIRECT_SIGNUP`)
- Event contact cards: `connect.caudals.com`, a separate static service in `services/connect` (Vite + three.js, nginx on atlantic). Permanent `/mario` and `/alonso` links negotiate `/es` or `/en`; each card page has a WebGL card whose reflections follow the phone's tilt (tap to flip), vCard, QR presenter (link or offline contact), WhatsApp/email hand-off of the visitor's details, Web Share and an offline service worker. Owner Wallet passes are issued through the WalletWallet API at build time, not at runtime. No database, secrets or evaluation-app dependency. See `services/connect/README.md`.
- Private operator access: `/auth/*`, `/api/auth/*` (retained internal-account auth)
- Evaluation: `/ops`, `/workspace`, `/review`, `/evaluation-entry`, `/share` and scoped `/api/evals/v1` APIs

The pre-pivot marketplace surfaces (`/buyer`, `/supplier`, `/v1/*`, `/security`, `/pricing`, `/docs`, `/about`, `/careers`, `/catalogue`) were deleted; they return `404`. There is no landing-mode flag: the routes above define the public and private product boundaries.

## Application Stack

- Framework: Next.js App Router (`next@16`), React 19, TypeScript
- UI: Tailwind CSS v4, Radix UI, shadcn/ui, custom primitives
- Data/Auth: self-hosted PostgreSQL + Better Auth + Postgres RLS
- Storage: S3-compatible object storage — private MinIO on the VPS, with DigitalOcean Spaces as the external managed target (`DO_SPACES_*` variable names serve both)
- Email: Resend
- Payments: Stripe hosted Checkout, Customer Portal and signed webhooks for credit top-ups and auto-recharge (launch L-12, test mode until Gate B); the marketplace checkout was removed; invoices and rectifying invoices through an invoicing adapter, `manual` (the accountant issues them from the monthly export) until a vendor is chosen (launch L-13)
- Observability: Sentry on the web app and the worker, scheduler and document services, scrubbed of personal data, with the deployed commit as release (launch L-08); platform alerts from the atlantic health timer and one-minute external uptime checks, both emailed with runbook links (`docs/evals/runbooks.md`). The retained Tempo/Loki/Prometheus/Grafana stack is not running. See `VPS_RUNTIME.md`
- CI/CD: GitHub Actions → Docker Hub → repository Swarm deploy scripts over Tailscale/SSH; retained Dokploy Traefik handles ingress
- Legacy dataset-build scope is frozen; runtime differs by stack. Temporal and social Redis are running; see "Legacy Private Stacks" and `VPS_RUNTIME.md`.

## Evaluation Product Implementation (feature-gated)

The current evaluation implementation uses `app/(evaluation)` for separate `/ops`, `/workspace` and assignment-scoped `/review` routes, `/api/evals/v1` for scoped APIs, `lib/evals` for typed evidence and execution, the `evals` PostgreSQL schema with additive migrations, and separate general, document, scheduler and browser workers. Workspace membership is verified server-side; tenant queries run under a non-owner, NOBYPASSRLS role. Stage C keeps registration invite-only, except self-serve free-plan sign-up from the public demo and direct work-email sign-up (see Public Demo). Website recipes are declarative and require validation before use; the deployed browser worker has a private egress gateway and DB relay, with synthetic acceptance recorded and customer recipes/authorizations checked per target. Stage D adds a customer-side outbound private runner and a separate gated scheduler service. Stage E adds redacted expert assignments, immutable submissions/reviews and privately delivered signed improvement datasets with family-aware splits and observational follow-up evidence. Stage E is disabled unless `EVALS_EXPERT_WORK_ENABLED=true` and the migration, role, trigger and Ed25519 release checks pass. See `evals/work-packages/WP-09.md`–`WP-15.md` for precise status and remaining release checks.

Engine models and lifecycle (migrations 063–064, 078–079):

- **Website context.** The browser reader follows the submitted page's public HTTPS redirects and uses the first captured page's final origin for its bounded crawl. Excerpts cite the resolved URL, including query parameters supplied by a redirect; linked pages stay on that final origin. The isolated HTTPS egress proxy validates and pins every destination connection, including intermediate redirect hops.
- **Model routes.** Each internal engine role (`context_analyzer`, `generator`, `judge`, `report_writer`) resolves to an evaluation choice (`evals.evaluation_model_route`), then a workspace route (`evals.generation_provider_route`) or the platform default (`evals.platform_model_route`); see `lib/evals/repositories/model-routes.ts`. Platform administrators choose models in Settings → AI models (`/api/evals/v1/engine/*`, `lib/evals/repositories/engine-settings.ts`), from the DGX Spark (Ollama tags) or any OpenAI-compatible API. DGX work stays `local_only`; commercial revisions run through the approved-provider path with the account's key from `evals.provider_connection` (an envelope bound to the nil tenant, readable only by the inference worker). Choosing a model registers an immutable provider revision and price revision, so every call stays budgeted and attributed. Source material is fitted round-robin to the model's context window; the workspace budget is created from the entitlement on first use. Platform administrators can also choose models per evaluation in the evaluation page's **1. Connect → AI models** panel (`/api/evals/v1/evaluations/[id]/models`), with one/all-task resets to defaults. These choices affect Caudals' engine; free workspaces reject external API overrides. Owners of paid workspaces can also run these roles on their own provider key (launch L-27, see Billing: Bring your own provider key).
- **Frozen job models.** Before insertion, each new generation job and run freezes all four effective routes in its immutable `model_routes` snapshot. The first generation call, later drafting rounds, grading and report narratives use the snapshot. Explicit retired evaluation models remain pinned so normal provider admission stops unavailable work. Pre-migration jobs have NULL snapshots and retain legacy workspace/platform resolution. Keep the additive schema when rolling back app/worker images; never drop model evidence or edit applied migration checksums.
- **Evaluation controls.** The evaluation's three-dot menu offers available pause, resume, stop and restart actions through `/evaluations/[id]/control`. Preparation persists operator intent separately from worker output (`generation_job.control_state`), so late completions cannot undo a pause or stop. Resume uses the saved job and its frozen models; provider errors with uncertain outcomes offer a fresh restart instead of replaying captured target work. Stop prevents pending calls and retains evidence; captured run answers may still be graded into a partial report. Restart saves one durable `evaluation_restart` request per evaluation, waits for running claims to drain, rechecks the requesting writer's live permission, then atomically creates one new preparation/run with current models and connection. The scheduler continues pending restarts with the page closed. Controls reject stale subject IDs, are idempotent and audited; creation failures retain a visible failed request. Migration 079 and the matching app/scheduler are one release unit. Never clear unknown outcome liabilities or worker fences to force a restart.
- **Evaluation queue.** Valid run requests and resumes enter a durable FIFO per workspace. General and browser workers take the same tenant advisory lock before claiming a run slot, bounded by the immutable `max_active_runs` entitlement. Waiting steps retry through the outbox without attempts or reservations; completion, cancellation or a fully drained pause frees capacity. Private runner polling and signed bundle downloads use the same admission check. Missing/disabled entitlements, exhausted budgets and unready connections remain denied. Migration 073 adds `queued_at` and read-only worker allowance grants; resume joins the end of the queue.
- **Worker scope.** The general, document, scheduler and browser workers serve their deploy-time `EVALS_*_ORG_IDS` plus every live workspace from `evals.worker_workspace_ids()`, refreshed every 10 s (30 s before launch L-06), so new clients need no redeploy. Every job still runs inside its own tenant scope under RLS.
- **Lifecycle.** Evaluations, systems, test sets, reports and reference material can be renamed and deleted (`/api/evals/v1/items/:kind/:id`). Delete archives (`archived_at`): the item leaves every list, share links of deleted reports are revoked, schedules pause, and immutable evidence follows the retention policy. Workspaces are renamed through `evals.rename_workspace()`; deleting a workspace remains the audited deletion workflow.
- **Notification centre.** Workspace-scoped notices show the latest event first, with per-person unread filtering and stable cursor pagination over 30 days. Started events appear only in Activity. The badge counts all visible unread notices, including older pages, and respects category preferences. Activity orders every job by its last durable update, with filters for work in progress, attention and completed work. Refresh failures remain visible; read state changes only after the server accepts the write. Workspace changes discard old requests and polling state.
- **Report exports.** PDF (document worker), editable Word (`lib/evals/reports/docx.ts`), CSV results and the CEF evidence bundle. Since launch L-17 the PDF and Word open with a cover (system, dates, status, whole-percent headline) and then the executive summary, "Fix these first" and the key takeaways; every page is numbered "Page n of N"; files download as `Caudals-<system>-<YYYY-MM-DD>.<ext>` (`lib/evals/reports/file-name.ts`). Stored PDF and Word files carry the document layout version in their path (`reports/<revision>[.es].v3.pdf`, `lib/evals/reports/version.ts`; 3 since the outcome stacks by topic and severity in "Results at a glance"); a request finds only files of the current layout, so a layout change renders a fresh copy instead of serving an old one (a share PDF made in the last ten minutes is still served, so an older worker during a rollout cannot loop).
- **Executive summary and fixes (launch L-17).** `lib/evals/reports/summary.ts` builds three sentences ("X of Y answers matched your sources…", the main problems, "Start with…"), the sample line and the status explanations from the snapshot's metrics and results only, through fixed EN/ES templates (`summary-copy.ts`); every sentence carries the result ids behind it. `lib/evals/reports/fixes.ts` groups failed and partly correct answers by likely cause (else failure category) and the source page their excerpt cites, ranks groups by severity weight and size, and keeps three to five; causes are labelled hypotheses. The web report, PDF and Word render the same objects (`tests/evals/report-cross-format.test.ts` checks it word for word). A shared copy without results keeps only the metric sentence. Fix lists export as CSV (one row per answer) and Markdown in the browser.
- **Shared report page (launch L-17).** `/share` explains what the report is, renders it, and ends with "Test your own assistant free" to `caudals.com/{locale}/demo?utm_source=shared_report&utm_medium=referral&utm_campaign=report_share&ref=sr-<hash>`. The exchange response's `meta.referral` is `sr-` plus 12 hex of SHA-256 of the workspace id (`lib/evals/reports/referral.ts`), never the id; the demo's first-touch attribution records it. Owners see "Opened N times, last on …" per link from `share_access_event` views (`open_count`, `last_opened_at` in the share list; `access_count` still counts views and downloads). Expiry presets are 7, 30 and 90 days; the API still accepts any `expiresAt`. The report's "Book a readout" opens the `CALCOM_LINK` booking page with `metadata[source]=report&metadata[workspace]=<hash>` and is tracked as `readout_link_clicked {surface: report}`; "Request expert review" opens `caudals.com/{locale}/contact?offer=pilot-evaluation` while `EXPERT_REVIEW_ORDERS_ENABLED` is off; with it on, the in-app request (L-26) replaces the link.
- **Customer API and webhooks (WP-13; contract and reference, launch L-20).** `lib/evals/monitoring/customer-api.ts` is the one definition of the token scopes (`runs:read`, `reports:read`, `schedules:read`, and since L-19 `runs:write`), the read endpoints and the fields they return (`GET /api/evals/v1/integrations/{runs,reports,schedules}?orgId=…`, newest 100; `GET …/integrations/ci/{scheduleId}?orgId=…`, the latest scheduled outcome), the webhook events and headers, and the limits. The routes select exactly those fields, and Settings → Developers renders its API reference (`components/evals/api-reference.tsx`, curl examples, Node and Python signature verifiers tested against the real signer in `tests/evals/api-reference.test.ts`) from the same constants. Every token request is limited to 60 a minute per token (`consumeRateLimit`, key `customer-api:<token id>`, counted after the token is validated); over the limit the API answers 429 `RATE_LIMITED` with `Retry-After`. Webhooks: canonical-JSON body, `x-caudals-signature: v1=hex(HMAC-SHA256(secret, id.timestamp.body))` with the base64url-decoded secret, five attempts with 1/2/4/8-minute waits, 10 s timeout, redirects refused.
- **Schedules on credits, re-run and compare, regression summaries (launch L-18, migration 095; no new flag).** Schedules (`lib/evals/monitoring/schedules.ts`, WP-13) are open to every workspace whose entitlement has `can_schedule`: pay as you go gets it with plans v2 (L-14), managed by contract. Workspaces that pay with credits schedule weekly or monthly (daily stays for contracts) and may give a schedule a credit limit: the most its runs may use in a UTC month (`billing.spend_cap` scope `schedule`, owners only through `billing.set_spend_cap`, which 095 limits to a schedule of the same workspace; audited; changing it does not change the schedule's version). Each due slot that passes the WP-13 checks is checked for credits before its run exists (`schedule-credits.ts`, in a savepoint): the schedule's month spend (captures and meters of its runs minus refunds plus open holds) plus the run's p90 against its limit, the balance (or an auto-recharge that covers it) against the p90, then the workspace's monthly and fixed per-run caps; what it saw is stored on `schedule_dispatch.admission`. Where credits are enforced (`BILLING_ENFORCE` or the workspace's override) a short slot is skipped with `credits_exhausted` or `cap_reached` and alerted (`skip-alerts.ts`: one notice `schedule_skipped`, billing category, and one `schedule_skipped` email per owner who keeps billing email on, claimed in `billing.alert_state` per dispatch, retried by later ticks, Stripe test mode emailing only Caudals' addresses); in shadow mode the verdict is recorded and the run starts; contracts are never checked. Runs then go through `createSelfServiceRun` (admission, L-11 holds, captures and meters with the run id). The billing watch also pauses a scheduled run whose schedule reached its limit (`cap_reached`, alert once per schedule and month). DST and catch-up rules are unchanged (`calendar.ts`). After each scheduled run (once its report exists, or 30 minutes after it finished) `alerts.ts` classifies it against the schedule's previous completed run as before and builds a summary (`summary.ts`: both scores, up to five newly broken questions most severe first, fixed count, `comparable`), stored in `regression_alert.evidence.summary` and handed to every destination (`destinations.ts`) in the alert's transaction: the in-app notice `monitor_<status>` (score against last time and the newly broken questions with links in the notification centre), the signed webhook (unchanged), and L-19's Slack/Teams destinations through `registerSummaryDestination`. A `monitor_regression` notice is emailed (`monitor_regression` template, EN/ES) to members who keep the regressions category on (on until a person saves a choice; operators opt in); runs that cannot be compared (another test set, rubric, grader or conditions) are `inconclusive` and never alert. Results and reports show "Run again" (the frozen test set, after the L-15 estimate where billing shows), "Compare", and, from the second run, the comparison with the previous run on their own (`GET /api/evals/v1/runs/:id/comparison`, `run-comparison.ts`, read-only; `components/evals/run-comparison.tsx`); L-17's "Re-run these questions" asks first and runs the whole approved test set again so scores stay comparable, listing the fix's questions first.
- **Integrations v2: CI trigger, release gate, Slack/Teams/email destinations (launch L-19, migration 096, `INTEGRATIONS_V2_ENABLED`, server-read, default off; app and scheduler).** A fourth token scope, `runs:write`, offered only with the flag and limited to 90 days (database check: 91), creation and revocation audited (`api_token.created`/`.revoked`; `api_token_created` reports `ci` for these tokens). `POST /api/evals/v1/integrations/runs?orgId=…` (`lib/evals/monitoring/ci-runs.ts`) takes `{suiteVersionId, targetRevisionId[, evaluationId]}` and an `Idempotency-Key` (8–200 visible characters): under a transaction advisory lock on the workspace and key, a replay answers 200 with the same run, the same key for another body 409 `IDEMPOTENCY_CONFLICT`, otherwise the run is created by `createSelfServiceRunInTransaction` (plan allowance and connection types, euro budgets, L-11 credit admission at the L-10 p90, L-15 monthly and per-run caps) and recorded in `evals.api_run_request` (unique per workspace and key, token provenance, immutable) in the same transaction, so each key starts exactly one run under concurrent retries; the run's `created_by` and the audit event `run.started_via_api` name the token (the key only as a hash). 30 new runs an hour per workspace on top of the 60 requests a minute per token; collected-answer systems are refused (422). The answer carries the L-10 estimate where the workspace pays with credits. `GET …/integrations/runs/{runId}/gate?orgId=…` (`runs:read` or `runs:write`) answers `pass`/`fail` against the threshold set on the schedule that started the run, else on its test set (`suite.gate_threshold`, `monitor_schedule.gate_threshold`, 0–100 % with two decimals, exact comparison on pass/scored; owners and operators, audited `gate.threshold_saved`; changing it keeps the schedule's version), `unknown` when the run failed, was cancelled or paused, fewer than 90 % of its questions or any critical one were graded, nothing was scorable, or no threshold is set, and `pending` (with `Retry-After: 30`) while it runs or is graded. **Destinations** (`webhook_endpoint.destination_type`: `webhook` unchanged, `slack`, `teams`, `email`): Slack URLs must be `https://hooks.slack.com/services/…` (or Slack GovCloud), Teams URLs keep their signed query string (`validatePublicDestination(…, {allowQuery})`, the only caller that allows one), email addresses must be a verified member's or a work address on a member's company domain (`evals.workspace_member_emails`); every URL passes the webhook egress checks (HTTPS, every DNS answer public, socket pinned to the checked address, no redirects, 10 s). For the three new types the URL or address is the credential: it is kept only in the endpoint's envelope (webhook keyring), `url` stays NULL and `target_hint` holds a masked hint. Each has a message language, "Send test" (`POST /webhooks/:id/test`, a labelled example sent from the app, five a destination per hour, result stored on the destination, audited) and deletion (`DELETE /webhooks/:id`: `archived_at`, disabled for good, audited). L-18's summary reaches them through `registerSummaryDestination` (`integration-destinations.ts`): one `webhook_delivery` per destination and event with the summary in its payload, queued in the alert's transaction only while the flag is on in the scheduler, then formatted by the scheduler's webhook tick (`destination-format.ts`: Slack Block Kit with a plain-text fallback, a Teams Adaptive Card 1.4, the branded `monitor_summary` email; EN/ES from the email catalogue; links to the report, each newly broken answer, or the evaluation) with the same five attempts; the generic signed webhook's queue and body are unchanged. Workspace deletion now revokes API tokens and disables destinations.
- **Better document intake (launch L-34, migration 098, `INTAKE_V2_ENABLED`, server-read, default off).** Prepare accepts drag and drop of up to 50 files (TXT, MD, DOCX, PDF, CSV, XLSX; 25 MB each, 200 MB per evaluation; the classic picker keeps 20 files and 100 MB): type and size are checked in the browser (`lib/evals/intake/upload-plan.ts`), copies are skipped by SHA-256 (in the batch, and on the server: `createUpload` answers a file already in the evaluation as `duplicate`), and each file shows its own progress and outcome. **Import help centre** turns a help-centre or sitemap URL into one website source: `POST /sources/websites/preview` queues `evals.website_page_preview`; the browser worker (`discoverWebsitePages`, same guarded context and egress proxy as the reader) reads the start page or sitemap, robots.txt (RFC 9309, `lib/evals/connectors/robots.ts`; an unreachable robots.txt reads nothing) and the origin's sitemaps (index children on the same origin only, at most 12 fetches), and lists up to 500 same-origin pages inside the optional path prefix; it never fetches another origin. The person selects up to the plan's cap (`websitePageCap`: 50 without plans v2 and on free, 200 on PAYG, managed and partner) with an estimate at the price book's `web_page_read` rate; the selected pages are stored on `website_source_job.selected_urls` and the reader reads exactly those (robots.txt checked again, no links followed, about 4 s a page up to 10 min, the 1 MB text budget still applies; `pages_read` recorded). The document worker records page count, characters and empty pages for every PDF; under ~50 characters a page on average or more than half the pages empty sets `scan_suspected` (`scan_detected {source_kind: pdf}`), and a PDF with no text fails as `pdf_scanned`; Prepare asks for a text version, the web page or leaving it out, and never blocks other sources. No OCR. **"What we understood about your assistant":** a generation a person starts with the flag on records `evals.context_confirmation` (`requested`); when the inferred profile is ready, drafting waits (`needs_input`, reason `context_confirmation_required`, the cited excerpts stored as evidence) for one confirmation: corrections become a new `context_profile_revision` (author and time on the revision and the confirmation row, edited fields, audited `context.confirmed`, `context_confirmed {edited_fields}`), skipping or 30 minutes without an answer (the scheduler) keeps the inferred revision. Every generated test carries `extensions["caudals.evals/context-profile"]` (revision, confirmation, status), and a report whose tests come from a skipped context lists "Context not confirmed by the customer." in its methodology. Onboarding auto-starts and restarts do not wait. Workers do not read the flag.
- **Help centre (launch L-20).** Twelve EN/ES articles in `content/help/{en,es}/<slug>.md` (front matter: title, summary, keywords, related, owner, `reviewed`, `review_by`; a small Markdown subset, `lib/evals/help/markdown.ts`). `scripts/evals/build-help.ts` writes `lib/evals/help/generated/{en,es}.json`; the help panel imports one language on demand and searches it in the browser (`searchHelp`: title, keywords, headings, summary, body; accent- and stop-word-insensitive), and `/workspace/help` and `/workspace/help/[slug]` (signed in) render from it in the person's language. The content lint (`lib/evals/help/content.test.ts`, in the image build) checks front matter, EN/ES parity (owner, dates, related, section anchors, links), links, claims and that the generated JSON matches the Markdown; `review-dates.test.ts` (not in the build) fails once an article is past `review_by`. Contextual "?" links (`HelpLink`, `CONTEXT_HELP`) open an article section in the panel from Connect, Prepare, Run, Results and Monitoring.
- **Readout mode (launch L-35, migration 099, `READOUT_MODE_ENABLED`).** `/workspace/reports/:id/present?revision=` shows a report revision as a slide sequence for a live readout: cover (system, dates, scope, review status) → verdict (the executive summary) → causes (the report's "Likely causes" and "Why answers failed" counts, labelled hypotheses) → five to seven transcripts (by default the most severe failure for each cause; each with its T number, result id and source excerpt) → "Fix these first" → next step (pilot or monthly monitoring, preselected from the plan: `managed` → monitoring, otherwise pilot). `lib/evals/reports/readout.ts` builds the deck only from the snapshot through the report's own builders; one HTML template (`readout-document.ts`, slide units of 1/1280 of the slide width) renders the screen and the 16:9 PDF (`readout-pdf.ts`, 1280 × 720 px per page). `evals.readout_deck` stores per-revision transcript picks and next step (members read, operators write); `evals.readout_note` stores presenter notes per slide, readable and writable only by operators and platform admins (`evals.is_readout_operator()`: platform operator/admin or workspace operator; RLS returns nothing to owners, editors or viewers; no worker role has a grant). Notes default to the §7.5 script and never enter a deck, an export or a share. API: `GET/PUT /api/evals/v1/reports/:id/readout` (notes in the response for operators only), `POST …/readout/export` (an `export_job` of kind `readout_pdf` whose `readout` column holds only the transcript ids and next step, checked by the schema; polled through `/exports/:id`, downloaded through the report-artifact gateway as `Caudals-<system>-readout-<date>.pdf`), `POST …/readout/presented`. The document worker renders `readout_pdf` jobs to `readouts/<revision>[.es].<deck hash>.v1.pdf`. The flag is `operators` (operators and platform admins) or `true` (also owners and editors, without notes); viewers never present. The example evaluation presents read-only at `/workspace/example/present`, notes and picks kept on the device, no export.
- **Expert review: request to reviewed report (launch L-26, migration 101, `EXPERT_REVIEW_ORDERS_ENABLED`; orders and the bench also need Stage E).** Owners (and workspace operators) ask from the report's next steps or the evaluation's results with "Have an expert review this": scope, optional note, deadline and sector (`POST /api/evals/v1/reports/:id/expert-review`, schema `lib/evals/experts/review-contracts.ts`). `evals.request_expert_review` opens one request per published report (a second click returns it) with its `reply_due_at` (next working day, Europe/Madrid, weekends skipped) and writes an immutable Warmbly CRM draft (`evals.review_crm_draft`, operators only, `sent` false and `destination` warmbly checked in the table); the route then emails the founders once at the internal `COLLABORATION_NOTIFICATION_EMAIL` (`lib/evals/experts/review-email.ts`, no answers or contact addresses, Resend idempotency key). The customer sees "Requested — we'll reply within one working day", then the order's due date, then the delivery; quotes and orders are never visible to customers. Ops work in `/ops/experts` (Review requests and Bench tabs) and `/ops/experts/reviews/:id`: record the hand-written reply, decline, or create the order (`evals.review_order`: scope, sector, due date, hand-written quote in EUR, never credits) with one Stage E `authoring` assignment per expert. "Publish the reviewed revision" writes a new immutable revision of the current report with `expert_review {order_id, reviewer_count, reviewed_on, scope, note?}`, publishes it and notifies the workspace (`report_published` with `expertReviewers`; the L-07 email says experts reviewed the report); grades and `review_status` are unchanged (settle disagreements in the review queue first). The expert screens are localized (EN/ES) with due dates and SLA, Ctrl/⌘+S, Ctrl/⌘+Enter and Alt+G shortcuts, a visible autosave state and a guideline link.

Reports after a spot check are the usual preliminary reports.

## Public Demo

A no-signup, eight-question test of a visitor's AI system (founder decision 2026-10-05). It is deliberately separate from the tenant engine: no workspace, RLS, budget ledger or queue, so it stays fast and its abuse surface stays small.

- **Code:** `lib/demo/*` (engine), `app/(app)/api/demo/*` (API), `components/demo/*` and `app/[locale]/demo` (page), `services/evals-browser/demo-worker.ts` (website work), `app/api/evals/v1/signup` + `components/evals/self-serve-signup.tsx` (account).
- **Data:** schema `demo` (migration 075): `demo.run` (one row per test: pages read, questions, each stamped with the time it was stored (`at`, launch L-24), answers, verdicts, summary; deleted seven days after creation), `demo.llm_usage` (primary-model calls per UTC day), `demo.challenge_use` (spent proof-of-work challenges). Migration 083 adds the queue (`queued_at`, `started_at`), the report-by-email request (`notify_email_ciphertext`, `notify_requested_at`, `notified_at`), `model_used`, `fallback_cost_eur`, and `demo.fallback_usage(day, eur, reserved_eur, calls)`. Never a credential: API keys and curl headers live only in the web process's memory and are dropped when the run ends.
- **Flow:** with the queue on, a new run waits (`queued_at` set, `started_at` NULL) until it is admitted; the web process then runs it through `reading` (pinned HTTPS fetch of up to six same-site pages, robots.txt honoured, ranked toward help/pricing/conditions) → `writing` (one streamed call writes eight questions with answer, key facts and a verbatim quote; each is accepted only when the quote is found in the cited excerpt) → `asking` (APIs called from the web process, one per second; website chats asked by the browser worker in fresh contexts) → `grading` (one batch judge call, grading engine v2 semantics, deterministic pre-checks and a lexical fallback) → `done`. A 45-second lease lets a restarted process resume unfinished runs; the client polls `GET /api/demo/runs/:id` with an ETag. Each phase has a time limit (reading 5 min, writing 10, asking 12, grading 5; `lib/demo/config.ts`); a phase that runs over fails the run as `timeout_<phase>`, and a finished run is never written again.
- **Website chats:** the browser worker (`EVALS_BROWSER_DEMO_ENABLED=true`) finds the chat as soon as the run exists, using the connector's auto-detection, and the engine writes questions only after the chat is found, so a missing chat costs no model quota. The demo loop runs beside the platform's browser slot (one demo at a time, `EVALS_BROWSER_DEMO_PARALLEL` questions at once) and never blocks customer jobs. Pages that need a browser to render are read there too. The worker's role has column-level grants on `demo.run`.
- **Models:** DeepSeek V4 Flash on the DGX Spark (`DEMO_MODELS`, default `bluehawana/deepseek-v4-flash:iq2_m` via Ollama on the private network endpoint `http://192.168.70.19:11434/v1`), about two calls per demo. Local private inference runs with zero external cost or provider rate limits; `DEMO_DAILY_MODEL_CALLS` (default 200) bounds daily execution. OpenRouter free models (`DEMO_OPENROUTER_API_KEY`) remain supported as an optional external fallback or override. Platform administrators choose the preferred model in Settings → AI models → Public demo (`/api/evals/v1/engine/demo`), from the configured demo provider's live model catalog (free models only on OpenRouter). The audited choice is saved in `demo.model_setting` (migration 076), bound to the provider endpoint's hash. The web runtime can read it; only the configuration-admin role can write it. Each completion resolves the preference without a restart, then retains the `DEMO_MODELS` fallback chain. With no saved preference, the environment/default model order applies.
- **Queue (`DEMO_QUEUE_ENABLED`, L-03):** a FIFO queue replaces the `busy` and `capacity` refusals. The web process admits the oldest waiting run (`lib/demo/queue.ts`, under a transaction advisory lock, so a rolling deploy cannot over-admit) while fewer than `DEMO_MAX_ACTIVE` (3) runs are in progress, fewer than `DEMO_MAX_ACTIVE_WEBSITE` (2, the browser worker's `EVALS_BROWSER_DEMO_CONCURRENCY`) website runs are, and a model can serve it. An API run may pass a website run that waits for the browser. Visitor and site limits are unchanged; `DEMO_QUEUE_MAX` (50) waiting runs is a safety valve (`queue_full`). The page shows the place in line and an ETA range from the median and 90th percentile of the last 50 finished runs (defaults 4 and 8 minutes). A run that loses model capacity mid-way goes back to the head of the queue with its work kept, rather than failing; one that waits longer than `DEMO_QUEUE_MAX_WAIT_MINUTES` (360) fails as `queue_timeout`. The browser worker serves admitted runs only and hands a re-queued run back.
- **Fallback model (`DEMO_FALLBACK_ENABLED`, L-03):** the primary is tried first; a rate limit, timeout, 5xx or spent daily call quota opens an in-process circuit (`lib/demo/health.ts`, two minutes) and the call goes to one commercial model, `DEMO_FALLBACK_MODEL` (default `google/gemini-3.1-flash-lite`) at `DEMO_FALLBACK_ENDPOINT` (default OpenRouter) with `DEMO_FALLBACK_API_KEY` or `DEMO_OPENROUTER_API_KEY`. Every fallback call first reserves its worst-case cost (input at one token per three characters, all output tokens, +25 %, at `DEMO_FALLBACK_INPUT_EUR_PER_MTOK` 0.25 / `DEMO_FALLBACK_OUTPUT_EUR_PER_MTOK` 1.5) in `demo.fallback_usage` with one conditional upsert against `DEMO_FALLBACK_DAILY_EUR` (default 5), then settles the provider-reported cost (USD counted 1:1 as euros, `DEMO_FALLBACK_USD_EUR`); an interrupted call keeps its hold, so concurrent calls never exceed the cap. The run records `model_used` and `fallback_cost_eur`. When neither model can serve (DGX down and the cap reached, or the key refuses to spend), the run waits in the queue and the page says so. `DEMO_FALLBACK_FORCE=true` skips the primary (DGX maintenance, verification). The demo footnote discloses that a backup model from Google, through OpenRouter, may read the public pages.
- **Report by email (with the queue):** a waiting or running test offers "Email me the report when it's ready" with a consent checkbox. The address and the run's private token are stored only as an AES-256-GCM envelope under the master keyring (`EVALS_MASTER_KEYRING_FILE`, purpose `demo_notify`, `lib/demo/notify.ts`). When the run ends the web process emails that address alone (Resend, idempotency key per run): the private report link, then deletes the envelope and sets `notified_at`; the sweeper retries for an hour, then drops the request. Startup instrumentation resumes the loop without requiring another visitor. Request bodies stay identical across email retries; signup remains an explicit action from the report. Three requests per visitor a day.
- **Events and status:** `demo_started` (target kind, docs given, locale, queue wait) when a run first leaves the queue and `demo_finished` (outcome, error code, duration, scored, correct, model used) when it ends, both server-side from `lib/demo/events.ts` into `product_analytics_event` (taxonomy owned by L-02). `GET /api/demo/challenge` and each run's view carry a service level (`ok`, `degraded` when the primary is down and the fallback answers, `capacity` when nothing can) for the page's notice.

## Example evaluation and sample report (launch L-33)

One synthetic evaluation of a fictitious insurer's home-policy assistant ("Hogarel", product "Hogar Completo") shows what a finished evaluation looks like (spec P-55). It exists only as versioned fixtures, never as database rows:

## Billing: Credit Ledger

Self-serve usage is paid in credits (launch spec v2 §6). **1 credit = €0.01 excl. VAT**; the ledger stores micro-credits (1 credit = 1,000,000 µcr) as `bigint` (`*_ucr` columns, `lib/billing/units.ts` for exact maths). Credits sit on top of the euro budgets in `lib/evals/budget/ledger.ts`, which remain Caudals' own cost guardrails. Package status: the ledger core (L-09, migration 084) is deployed; the price book, €0 model guard and run estimator (L-10, migration 088) are live (estimates behind a flag); the engine hooks (L-11, migration 089) hold, capture, release and meter on the real execution path, in shadow mode for the shadow week; Stripe (L-12), plans v2 with the monthly allowance and per-workspace overrides (L-14, below), the customer billing screens with caps and alerts (L-15, below) and the ops console (L-16) build on them.

- **Data (schema `billing`, migration 084):** `credit_account` (one per workspace: `billing_mode` free/credits/contract, `available_ucr`, `held_ucr`, `frozen_reason`, `version`), `credit_lot` (one per purchase, grant, allowance or bonus: source, granted/remaining/held/expired µcr, euro unit price paid, expiry, order), `credit_hold` (one per key: held → captured, released or expired) and `ledger_entry` (append-only: a trigger rejects UPDATE, DELETE and TRUNCATE). Each entry records the signed change of available + held (`amount_ucr`), both bucket deltas, the balances after it, the lots it touched, a per-workspace idempotency key and request fingerprint, references (run, attempt, case unit, price-book revision, Stripe/ref ids), the actor and its kind, reason and request id. `verification_run` keeps the nightly verifier's results.
- **Writes** go only through `SECURITY DEFINER` functions, each idempotent by key and writing the entries and balances in the caller's transaction: `billing.grant`, `hold`, `capture` (capped at the hold, rest released), `release`, `charge_action`, `adjust`, `reverse`, `refund_run`, `expire_due`, `verify_account`, `record_verification`. A replay returns the original entry; a replay with different values raises `IDEMPOTENCY_CONFLICT`. Corrections are reversal entries. Typed wrappers and error classes (`BillingError`, `CreditsExhausted`) are in `lib/billing/ledger.ts`.
- **Access:** RLS by `org_id`; `evals_runtime` (web and scheduler) and the worker roles (`evals_worker`, `evals_browser`, `evals_document`) can only read their scoped workspace's rows. Tenant functions act only on the transaction's `evals.org_id`. Holds, captures, releases, platform charges and per-account verification are granted to the runtime and every worker role; credit creation, corrections, run refunds, expiry and the platform-wide verifier are granted only to `evals_runtime` and, inside it, accepted only from platform admins (with a required, audited reason) or `service:`/`system:` identities. Workers never create credits.
- **Lots:** holds and spends take the unheld part of unexpired lots oldest-expiring first (never-expiring last); a capture consumes the hold's own lots in that order. Expiry removes only the unheld part of a lot; any spend expires due lots of its account first, so expired credit is never spent. Defaults (D-10, `lib/billing/config.ts`, configurable): purchases and their bonus 24 months, promos and ops grants 30 days, the monthly allowance at UTC month end, contract allowances at the contract end supplied by the caller. Default periods end at the end of their last UTC day so a retried request replays.
- **Lock order:** provider account → workspace and run budgets → `billing.credit_account` → lots and holds. Every billing function locks the workspace's account row first and never touches the evals budget rows, so per-workspace billing writes serialise on that row and cannot form a cycle with `reserve()`/`settle()`. Call billing functions after the budget locks in the same transaction.
- **Accounts:** the migration backfilled one zero-balance account per workspace (plan `managed` → `contract`, `free` → `free`); a trigger on `evals.workspace_entitlement` creates the account for new workspaces and keeps `billing_mode` in step with the plan (other plans → `credits`).
- **Invariants (§6.9), checked by `billing.verify_account`:** available ≥ 0 and held ≥ 0; Σ entry deltas = balances; the last entry's running balance = the account; Σ lot remaining = available + held; Σ lot held = held = Σ open holds; every lot's remaining and held part equals the sum of the entries' allocations on it; captures never exceed holds; no lot goes negative or beyond its grant; a replay never creates a second entry (unique key per workspace).
- **Jobs (evals scheduler, `lib/billing/jobs.ts`):** the verifier runs at scheduler start and in the 03:00 UTC hour, records a `billing.verification_run`, and logs `billing_verified` or `billing_drift` (workspace ids and issue codes only). Expiry (`expire_due`, hold expiry after 24 h by default and lot expiry) runs hourly when `BILLING_CREDITS_ENABLED=true`.
- **Flags (server-side, app credentials; the evals deploy copies them to the worker, scheduler, browser and document services):** `BILLING_CREDITS_ENABLED` (default `false`) and `BILLING_ENFORCE` (`shadow` default, or `enforce`; turning enforcement off returns runs to the entitlement and euro-budget checks). `BILLING_STRIPE_MODE` and `BILLING_TEST_WORKSPACE_IDS` belong to payments (below).
- **Rollback:** `db/rollbacks/084_billing_core_down.sql` refuses once any entry, lot or hold exists or an account has a balance or freeze; repair forward.

### Price book, €0 guard and run estimates (L-10, migration 088)

- **Price book:** `billing.price_book_revision` moves draft → scheduled → active → retired. Each revision carries `model_rate` rows (µcr per 1M input, output and optional cached tokens, keyed by provider, model id and a prompt-size tier, with a cost snapshot: USD list price, FX, routing fee, the EUR cost and its source) and `action_rate` rows (the six §6.3 meters). Rates are editable only on drafts; triggers reject changes to scheduled, active and retired revisions (only lifecycle columns move) and any TRUNCATE. The database enforces the §6.4 grid: every rate is a multiple of 5 credits per 1M with a 10-credit floor. The arithmetic (cost × FX × fee × multiplier 1.5 × 100, rounded up) is in `lib/billing/price-book.ts` and reproduces the §6.4 table exactly.
- **Which revision applies:** `billing.price_book_at(t)` is the non-draft revision with the latest `effective_at` at or before `t`, so a scheduled revision applies exactly on its date; the scheduler's hourly `activate_due_price_books()` only relabels statuses and audits. Seed: revision 1 (in effect from 2026-10-11, the §6.4 table and meters, ECB 1.1605 USD/EUR) and revision 2 (scheduled 2027-01-01: Google's announced Gemini 3.8 Flash increase). L-11 freezes the revision id into runs; `ledger_entry` and `credit_hold` now reference it.
- **Changes:** `billing.create_price_book_draft` (from the revision in effect, recomputing list prices at the latest recorded FX, then applying per-model changes), `schedule_price_book` (needs every meter and the local rate, must follow every other scheduled revision, keeps every current customer route priced, and refuses an increase with less than 30 days' notice), `cancel_price_book` (before it takes effect) and `activate_price_book` (brings a non-increase forward to now). Platform admins (recent sign-in, `Idempotency-Key`) through `/api/evals/v1/billing/admin/price-book/revisions[/:id[/schedule|/activate|/cancel]]`; every step writes `evals.audit_event`. Notices for increases are sent by L-16.
- **€0 guard (G9):** a trigger on `platform_model_route`, `generation_provider_route` and `evaluation_model_route` refuses a model whose cost price is €0 (`MODEL_PRICE_ZERO`; the DGX is capacity-priced and exempt) or that has no credit rate in the revision in effect or any scheduled one (`MODEL_RATE_MISSING`), unless its provider revision is an explicit `free_model` (fixed at registration; registered OpenRouter `:free` models were flagged by the migration). `billing.route_price_issues()` lists every route's status. Settings → AI models and Providers & models show each model's credit rate, a "€0 price · not for customers" warning and the free-model choice. Local stays the default route (D-09).
- **Estimates (§6.7):** `lib/billing/estimate.ts`. Questions × repetitions by connection kind are metered exactly (website 5, API 2, imported answer 1 credit; pages 1 and 0.5; web searches 2). Engine tokens per role use platform-wide aggregates from `billing.estimate_stats` (SECURITY DEFINER, aggregates only) over 60 days: per role and model from 20 samples, else per role, else the §6.7 seeds. The median of a run is n × mean per call and its p90 adds 1.2816 × sd × √n. Output: p50/p90 credits and euros, the largest single hold (rate × the p90 token bound), an ETA from seconds per question of completed runs (below 20 measured runs the tail is capped at twice the median), and the credits to add (none for `contract` workspaces, which run without holds). `POST /api/evals/v1/billing/estimates` serves editors (owner, editor, operator) and CI tokens (`runs:read`), with an `Idempotency-Key`; `BILLING_ESTIMATES_ENABLED` = `operators` (platform staff and workspace operators only) or `true` (everyone), anything else 404. Enforcement is L-11.
- **Prices over time:** the scheduler runs a weekly provider-price check (OpenRouter's public models API; Google-direct rows compared with OpenRouter's listing of the same model) into `billing.price_check` and logs `billing_price_check_changes` when a listing moved; it records the ECB USD rate monthly (`billing.fx_rate`). Rates whose cost moved more than 3 % (price or FX) are flagged for a new revision. `scripts/billing/check-provider-prices.ts` prints the same diff; `scripts/billing/backtest-estimates.ts` measures estimate accuracy on read-only production aggregates.
- **Rollback:** `db/rollbacks/088_billing_price_book_down.sql` refuses once a ledger entry or hold references a revision, an operator revision, FX rate or price check exists; repair forward.

### Engine hooks, shadow mode and run refunds (L-11, migration 089)

- **Where credits move** (`lib/billing/engine.ts`, called inside the engine's existing transactions after the euro budget locks, so the lock order stays provider account → workspace and run budgets → `billing.credit_account` → lots):
  - `InvocationWorker.claim()`: right after `reserve()`, a hold `attempt:<attempt_id>` of the model rate × the call's token bound (the euro reservation's bound; cached input at the dearer input rate). Only engine roles are charged (generator, context analyzer, judge, report writer); probes and target calls are not.
  - Success: after `settle()`, a capture of rate × the provider's usage (or, without usage, the prompt bound and the answer's bytes capped at the output bound), capped at the hold; the rest is released. An incomplete answer is released, not charged. A completed web search adds `search:<attempt_id>` (web_search_query × queries).
  - Release: `finishFailure` (known failures), a cancel before dispatch and `recover()` for calls never dispatched. A dispatched call with an unknown outcome keeps its hold; `billing.expire_due` releases it after 24 hours (hourly in the scheduler), so failed, cancelled and unknown calls cost the customer 0.
  - Platform meters (`billing.charge_action`, key `unit:<case_unit_id>`): website and API questions when the target worker records a `succeeded` observation, API questions for private-runner answers, graded answers when `scoreRun` grades an imported answer, and finalized sources (`source:<revision_id>`: website pages read, PDF pages, or 3,000 characters a page for other documents). Never for `capture_incomplete`, `timeout`, `target_error` or unknown outcomes.
  - Pricing comes from `billing.engine_pricing` / `billing.action_pricing` (SECURITY DEFINER, tenant-checked): the account's mode and balance, the run the work belongs to (a run workflow, a judge job or a report narrative job) and the price-book revision frozen on that run or generation job.
- **Price-book snapshot:** a trigger freezes `price_book_revision_id` (the revision in effect) into every `evals.run` and `evals.generation_job` at insert, next to `model_routes`; changing it raises `immutable job price book`. Rows from before 089 are priced at the revision in effect when they were created.
- **Admission** (enforce mode): `createSelfServiceRun` (API start, schedule dispatch, evaluation restarts, later the CI trigger) refuses with `402 CREDITS_EXHAUSTED` ("Add N credits") when available credits are below the estimator's p90; resuming a paused run needs the p90 of the questions still to run. Contract workspaces are never gated and never hold credits.
- **Pause and resume:** `CreditsExhausted` at a claim (or a meter the balance cannot pay in full, which is charged partially and never refuses finished work) pauses the workflow with `credits_exhausted` (`lib/evals/queue/credit-pause.ts`): queued steps pause, running ones drain, and a run shows "Paused — add credits to continue" (EN/ES). Target claims check the next question's meter first. `controlRun(resume)` re-queues, and `resumeCreditPausedWork` resumes every workflow of the workspace paused for `credits_exhausted` or `cap_reached` (grading, report and generation passes too). `cap_reached` is reserved for the caps of L-12/L-14.
- **Modes:** `BILLING_CREDITS_ENABLED=false` runs none of this (no query). `true` with `BILLING_ENFORCE=shadow` records what enforce mode would hold, capture, release, charge, admit and refund in `billing.shadow_entry` (append-only, RLS, no foreign key to the account): each write runs in its own savepoint with a 500 ms lock timeout, never locks the credit account, never raises for a short balance (`would_block` records it) and swallows every error (`billing_shadow_error` log line), so shadow mode cannot fail, pause or block a run; contract workspaces are recorded too, flagged `contract`. Shadow admissions are computed by the scheduler for runs started in the last five minutes, off the request path. `enforce` moves credits. The amounts come from the same functions in both modes.
- **Reconciler (scheduler, hourly while credits are on):** releases shadow holds unsettled after 24 hours and refunds every failed run (no usable result) that still carries captures or meters, once, with `billing.refund_run` (`run-refund:<run_id>:<entry>`) or its shadow counterpart.
- **Shadow diff:** `billing.shadow_diff(day, org?)` compares a UTC day of shadow entries with `budget_reservation`, attempts, units and usage: completed calls without a capture, captures without a completed answer, captures whose requested credits differ from rate × usage recomputed in SQL, meters without a succeeded unit, succeeded units of shadow-admitted runs without their meter, and shadow holds open after 25 hours. The scheduler keeps a daily report (`billing.shadow_report`, 04:00 UTC for the previous day; log `billing_shadow_report`, or `billing_shadow_mismatch` as an error) and the health check alerts `billing_shadow_drift` when the latest report has mismatches. `scripts/billing/shadow-report.ts` prints it on demand.
- **Monthly workspace budget (G8):** `evals.execution_budget` gains `period_start` and `period_base`. The workspace budget's ceiling applies to `settled − period_base`; the first `reserve()` or `settle()` in a new UTC month moves the base to the lifetime `settled`, so lifetime spend no longer trips "budget exceeded". Run budgets and provider accounts keep lifetime totals.
- **Rollback:** `db/rollbacks/089_billing_engine_hooks_down.sql` refuses once a run or job froze a revision or a shadow entry or report exists; repair forward. The kill switch is `BILLING_ENFORCE=shadow` (or `BILLING_CREDITS_ENABLED=false`), set on the app and the workers.

Live mode opens top-ups to workspace owners only with `BILLING_CREDITS_ENABLED=true` and the real company data (`LEGAL_ENTITY_*`, D-01), and (L-14) only to workspaces a platform admin allowlisted (`billing.workspace_override.live_payments`, read by `resolvePaymentsAccess`) until `PLANS_V2_ENABLED` opens them to every owner at Gate B; pages, routes and the auto-recharge job all apply it. Every billing route and page answers 404 while closed. Webhook signing secrets are per mode (`STRIPE_TEST_WEBHOOK_SECRET`, `STRIPE_LIVE_WEBHOOK_SECRET`).
- **Data (schema `billing`):** `billing_profile` (legal name, country, normalised tax ID and kind `es_nif`/`eu_vat`/`non_eu_business`, VIES status and consultation, address, billing email, tax treatment or the manual-review reason, business declaration, ops limit lift), `stripe_customer` (per workspace and mode, with the card saved for auto-recharge: id, brand, last 4, country), `top_up_order` (kind `checkout`/`auto_recharge`, mode, status, net/VAT/gross cents, treatment, a snapshot of the fiscal details, base, pack and first bonus µcr, the bonus applied, Stripe session/intent/charge/customer/refund/dispute ids, card country, risk flags, attribution, ledger entry ids, idempotency key), `stripe_event` (event id primary key, type, mode, payload hash, deliveries, received/processed timestamps, status and outcome), `first_bonus_claim` (`org:`, `domain:` and `tax:` keys), `auto_recharge` (settings plus `armed`, `crossing_seq`, `in_flight_order_id`, failures, `retry_after`), `spend_cap` (monthly, per-run and per-schedule; edited and enforced by L-15, per-schedule caps by L-18) and `alert_state` (per-period deduplication of billing emails and alerts). RLS by `org_id`; `evals_runtime` reads its scoped rows and writes none; worker roles have no access.
- **Writes** go through `SECURITY DEFINER` functions. Owner functions (`save_profile`, `save_stripe_customer`, `create_top_up_order`, `attach_checkout_session`, `close_checkout`, `set_auto_recharge`, `set_spend_cap`) accept the workspace's owners, platform admins and service identities. Recording functions (`stripe_event_begin`/`finish`, `find_top_up_order`, `record_purchase`, `record_payment_details`, `record_payment_failure`, `begin_top_up_refund`, `finish_top_up_refund`, `record_charge_refunded`, `record_dispute`, `lift_purchase_limits`, `auto_recharge_due`, `claim_auto_recharge`, `attach_payment_intent`, `claim_alert`, `mark_alert_sent`) accept platform admins and service identities only: the webhook runs as `system:stripe-webhook`, the return-page sync as `system:stripe-sync`, auto-recharge as the scheduler.
- **Amounts are derived in the database:** the pack (€20/50/100/250/500 with 0/3/5/8/10 % bonus), 1 credit per euro cent, IVA from the profile's treatment (21 % in Spain and for EU businesses without a valid VIES number, none with reverse charge "Inversión del sujeto pasivo" or outside the EU "Operación no sujeta"; `lib/billing/tax.ts`, to be confirmed with the gestor), and the +20 % first top-up bonus, offered while the workspace, its buyer's company domain and its tax ID have no claim and settled at payment (the larger of the two bonuses applies, never both). Consumers are refused (D-05: a business declaration and a business tax ID). VIES is retried; when it stays unavailable, or the address is in the Canary Islands, Ceuta or Melilla, the profile has no treatment and checkout is refused until reviewed.
- **New-account limits (§6.15):** until 30 days after the first payment, orders in flight or kept total at most €100 net and at most 3 orders start per 24 h (`PURCHASE_LIMIT`, `PURCHASE_RATE_LIMIT`); ops can lift them per workspace (audited). A card country that differs from the tax country and Checkout fiscal details that differ from the profile are flagged on the order for the fraud queue (L-16).
- **Checkout (`lib/billing/checkout.ts`, `top-ups.ts`):** `POST /billing/top-ups` (owner, `Idempotency-Key`) creates the order, records Terms and Privacy acceptance with context `checkout` (L-01) and `top_up_started`, then opens hosted Checkout for the workspace's Stripe customer (kept in line with the profile, tax ID added): one line with the 21 % Tax Rate when IVA applies, the legal mention otherwise, card only, billing address and tax ID collected, `setup_future_usage=off_session` while no card is saved, 45-minute sessions, idempotency key `checkout-session:<order>`. Success and cancel return to `/workspace/billing/top-ups/<order>`, which polls `GET /billing/top-ups/:id`; that endpoint also asks Stripe for a pending session (every 3 s at most) and records a completed payment itself (`billing_webhook_lagging` when it got there first). Leaving Checkout expires the session and closes the order. The Customer Portal (`POST /billing/portal`) manages saved cards with a configuration limited to payment methods.
- **Webhook (`app/api/evals/v1/billing/stripe/webhook`, `lib/billing/webhook.ts`):** app host only, no session (`proxy.ts` passes it through); verifies the signature (5-minute tolerance) with the mode's secret and rejects events of the other mode. Each delivery is recorded in `stripe_event`; a processed or ignored event answers 200 again. The order is found by our metadata or its Stripe ids (the workspace in metadata is never trusted), falling back to the PaymentIntent's metadata when an event outruns our records. Handled: `checkout.session.completed`, `checkout.session.expired`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `charge.refunded`, `charge.dispute.created` and `.closed`. Purchases go through `record_purchase` (purchase lot priced per credit and bonus lot unpriced, both 24 months; keys `purchase:<order>` and `purchase-bonus:<order>`), so Checkout completion, `payment_intent.succeeded`, replays and the return-page sync credit an order once, within the request that delivers the payment. A failed payment adds nothing; a failure after a success changes nothing; a refund or dispute that arrives before the payment reconciles the payment from the PaymentIntent first, or answers 503 so Stripe retries. Permanent mismatches are recorded as failed and acknowledged. On first payment the workspace's saved first touch is copied to the order and sent with `top_up_paid` (L-02).
- **After payment (`follow-up.ts`, `emails.ts`):** card details and risk flags from the charge; the saved card becomes the customer's default; the receipt (L-07's `payment_receipt` template with the top-up's fiscal lines, EN/ES by billing country, a receipt rather than an invoice) is sent once per order to the billing email. Auto-recharge failures use `auto_recharge_failed` and go to owners who keep billing email on. In test mode billing emails go only to Caudals' own addresses.
- **Refunds (`refunds.ts`, `POST /billing/admin/refunds`):** an untouched purchase within 14 days (D-10). Ledger first: `refund` entries reverse the purchase and bonus (a `refund` may now be negative when it reverses an entry), audited; then the Stripe refund (`refund:<order>`); then the order is `refunded`. A Stripe failure leaves `refund_pending` for a retry or the `charge.refunded` webhook. A refund made in the Stripe dashboard is mirrored (untouched: the same reversal; otherwise what is left is removed and the shortfall flagged). Above €100 net a second approver is required (L-16).
- **Disputes:** opening one freezes the account (`dispute:<id>`; no new holds or purchases, work in flight finishes); won or withdrawn lifts it when no other dispute is open; lost writes a `chargeback` entry removing what is left of the order's credits, never below zero (the shortfall is in its metadata and flagged), and leaves `chargeback:<id>` for ops.
- **Auto-recharge (`auto-recharge.ts`, evals scheduler every minute):** off by default; settings via `PUT /billing/auto-recharge` (threshold, pack, monthly cap of recharges and euros; needs a saved card). `claim_auto_recharge` decides under the account lock: re-arm when the balance is back at or above the threshold, open the next crossing with an order when it drops below, retry once 24 h after a failure, then switch off. The saved card is charged off-session with the idempotency key `auto-recharge:<workspace>:<crossing>:<attempt>`; one recharge is in flight per workspace and a crash resumes it with the same key. Failures write an in-app notice (`auto_recharge_failed`) and the webhook emails the owners, with a 24-hour Checkout link when the bank asks for authentication. Events `auto_recharge_paid` and `auto_recharge_failed`.
- **Rollback:** `db/rollbacks/091_billing_payments_down.sql` refuses once any payments row or a negative refund entry exists; repair forward.

## Billing: Plans v2, Monthly Allowance and Rollout Overrides

Launch L-14 (spec v2 §6.5, §6.10, §6.18; P-09; migration 093). Behind `PLANS_V2_ENABLED` (server-read, app and scheduler, default off; switched on at Gate B) or, per workspace, the admin override below. With neither, every behaviour equals the pre-L-14 one.

- **Plans:** `workspace_entitlement.plan` ∈ `free`, `payg` (any workspace that has bought credits), `managed` (contracts; unchanged) and `partner` (per agreement, L-28). Billing modes follow through the 084 trigger: free → `free`, managed → `contract`, payg and partner → `credits`. Limits live in the entitlement columns and are enforced by triggers: systems (`max_systems`, target insert), runs per calendar month (`max_runs_per_month`, run insert), questions per generated set (`max_tests_per_set`, trimmed at generation-job insert) and, new, members (`max_members`: owners, editors and viewers plus live invitations, checked at invitation insert; Caudals operators never count). Capped inserts lock the entitlement row (`FOR NO KEY UPDATE`) so two at once cannot both pass; uncapped (managed) workspaces skip the lock. Trigger errors carry `{org_id, limit}` in `DETAIL`. The free limits are 1 system, 50 questions, 3 runs a month, 1 active run, website/OpenAI-compatible/HTTPS JSON connections, no schedules; PAYG adds 10 systems, 500 questions, no monthly run cap, 2 active runs, schedules, uploads (imported answers) and 10 members (`lib/billing/plans.ts`).

A refund does not downgrade.
- **Monthly allowance (`lib/billing/allowance.ts`, scheduler every minute while `BILLING_CREDITS_ENABLED=true`):** `billing.allowance_due(period, all)` lists live free and PAYG workspaces with an unfrozen account and no `grant:allowance:<YYYY-MM>` entry (all of them with `PLANS_V2_ENABLED`, otherwise only those with the `plans_v2` override); each gets `billing.grant(source allowance, 1,000 credits, expires at the next UTC month start)` with the key `allowance:<YYYY-MM>`, so concurrent schedulers or retries replay the same grant. Allowance lots have no price (no cash value, no VAT) and expire through `expire_due`. Work paused for `credits_exhausted` resumes after the grant. Log line `billing_allowance`.
- **Typed limits (P-09):** while plans v2 applies to the workspace, a trigger limit becomes `PLAN_LIMIT_SYSTEMS`, `_RUNS` or `_MEMBERS` (`lib/evals/domain/plan-limits.ts`, in the API error mapper), and code paths raise `PLAN_LIMIT_CONNECTION` (run start on a connection type outside the plan), `_SCHEDULES` (schedule creation) and `_QUESTIONS` (a person asking for a larger test set; restarts and onboarding keep the trim). Each is a 403 `PlanLimitError` whose body adds `limit: {kind, limit, connectionType}` and records `limit_hit {kind: <code>}` with the workspace. Otherwise the answer stays the generic `PLAN_LIMIT`. The app announces typed limits from `evalRequest` (`caudals:plan-limit`) and the shell's `LimitDialogHost` opens `components/evals/limit-dialog.tsx`.
- **Plan summary:** `GET /api/evals/v1/billing/plan?orgId=` (members; platform admins audited; 404 while plans v2 is off for the workspace): plan, limits with usage (`evals.plan_usage`, which can count members), the PAYG limits, what unlocks each limit (`credits` from free where PAYG adds it, otherwise `managed`), per-connection unlocks, the month's allowance, the balance for owners, editors and operators, and the dialog's actions (top-up for owners where payments are open, the booking page).
- **Rollout overrides (decision I-11 and the L-12 founder note):** `billing.workspace_override` (RLS by workspace; the runtime and every worker role read their own row) holds `enforcement` (`inherit` | `shadow` | `enforce`), `live_payments` and `plans_v2`, with a required reason and a version. Only platform admins change it, through `billing.set_workspace_override` (audited as `billing.workspace_override` with before and after; enforcement cannot change while a run is queued or running: `WORKSPACE_BUSY`) and `GET/PUT /api/evals/v1/billing/admin/overrides` (recent sign-in, `Idempotency-Key`). The engine resolves each workspace's mode in every hook (`workspaceEngineMode`, in a savepoint that falls back to the process mode): an override acts only while `BILLING_CREDITS_ENABLED=true`, which stays the kill switch; a call held in shadow mode is settled in shadow mode after a switch; contract workspaces never hold credits whatever the override. The scheduler records shadow admissions for workspaces in shadow mode either way.
- **Rollback:** `db/rollbacks/093_evals_plans_v2_down.sql` refuses once a workspace is on payg or partner, has a member cap, or any override exists; repair forward.

## Billing: Invoicing and IVA

Launch L-13 (spec v2 §6.13, §6.14, §6.16; migration 092; decisions D-04, I-1, I-4). Stripe is not a Spanish invoicing system: every paid top-up needs an invoice and every refund a rectifying invoice (*factura rectificativa*). No invoicing vendor is chosen yet (D-04), so the `manual` adapter is live and the accountant issues the documents from the monthly export.

- **Data (schema `billing`):** `invoice_series` (`CAU` credits, `CAU-S` services, `CAU-R` rectifying, each with the pattern an issued number must match; §3.2, to confirm with the gestor), `invoice` (one per paid order, `UNIQUE (order_id)`, series `CAU`) and `credit_note` (one per refunded order, series `CAU-R`, negative amounts, `invoice_id` = the original). Each document carries the buyer's fiscal snapshot from the order (legal name, tax ID and kind, VIES status and consultation, address, billing email), the operation date (Madrid), the language (`es` for Spanish buyers, else `en`), net/IVA/gross with the treatment and its legal mention (21 % IVA; "Inversión del sujeto pasivo"; "Operación no sujeta"; `billing.tax_mention` = `lib/billing/tax.ts`), the lines (purchased credits at 1 cent, bonus credits free), the provider and its references, the Verifactu status, the PDF (`pdf_object_key`, SHA-256, size; private storage) and the retry state (`attempts`, `next_attempt_at`, `last_error_code`). `top_up_order.invoice_id` links the order. `invoice_document` is a security-invoker view over both. RLS by `org_id`; the runtime reads, never writes; workers have no access. The issuer (Caudals' entity) is never stored: it comes from `LEGAL_ENTITY_*` at runtime and the §3.2 placeholders are ignored (`lib/legal/documents.test.ts` fails the image build if invoice code, the export or the invoice email carries them).
- **Queueing:** a trigger on `billing.top_up_order` queues the invoice when `purchase_entry_id` is first set and the rectifying invoice when the status becomes `refunded` (our refunds and refunds mirrored from the Stripe dashboard), in the payment's transaction, whatever function moved the order. Replays and concurrent deliveries give one document. Partial refunds and chargebacks are flagged for the accountant, never rectified automatically. The migration backfilled earlier paid orders.
- **States:** `queued` → `pending_issue` (handed to the provider; the manual adapter's terminal step until ops attach the number) → `issued` (number, issue date, `issued_by`, optional PDF and Verifactu status). Live numbers must match their series; Stripe test-mode documents take `TEST-` numbers only, and only they can be `voided` (live documents are corrected by rectifying invoices). Nothing in the platform generates a legal number.
- **Adapter (`lib/billing/invoicing/index.ts`):** `syncCustomer`, `issueInvoice`, `issueRectifying` (with the original's number and reference) and `fetchPdf`, idempotent per document id. `manual.ts` accepts each request as pending issue and never makes up a number or PDF. A vendor adapter is added as `lib/billing/invoicing/<provider>.ts` once D-04 is decided; `tests/billing/fake-invoicing-provider.ts` proves the interface. `BILLING_INVOICING_PROVIDER` (`off` default, `manual`, or a vendor name) is read at runtime by the web app and the scheduler.
- **Job and retry queue (`jobs.ts`, evals scheduler every minute):** `billing.invoicing_due` (invoices before rectifying invoices) → `claim_invoicing` (counts the attempt, 10-minute lease; a rectifying invoice waits until its original is handed over) → adapter → `record_invoicing_handover` or `issue_invoice_document` (provider PDFs sealed in private storage, then "invoice available" emailed) or `record_invoicing_failure` (backoff 1, 2, 4 … 60 minutes). `scripts/evals/health-alerts.sh` raises `invoicing_stalled` (runbook 22) when a document has stayed queued an hour after a provider failure, or a day without any attempt.
- **Ops (platform admin, recent sign-in, `Idempotency-Key`, reason, audited):** `GET /api/evals/v1/billing/admin/invoices?status=&mode=` lists documents across workspaces; `POST /api/evals/v1/billing/admin/invoices/:id {action: "issue", orgId, kind, number, issueDate, pdfBase64, verifactuStatus?, reason}` records the accountant's number (checked against the series), date (not before the operation, the original's date for a rectifying invoice, or the future) and PDF (≤ 5 MB, sealed under `evals/<org>/<document>/sealed/<uuid>`), audits `billing.invoice_issued` and sends `invoice_available` (L-07 template, EN/ES, PDF attached) once to the billing contact; `{action: "void", reason}` voids a test-mode document. The L-16 console builds on these.
- **Owners:** `GET /api/evals/v1/billing/invoices?orgId=` (invoices and rectifying invoices, `pending` until issued) and `GET /api/evals/v1/billing/invoices/:id/pdf?orgId=` (the verified PDF, or the provider's, kept on first download). Owner only (platform admins read with an audited support check), 404 while invoicing is off. The Invoices tab is L-15.
- **Monthly accountant export (`billing.accountant_export(month, livemode)`, `lib/billing/invoicing/export.ts`, `scripts/billing/monthly-export.ts`):** for a Madrid calendar month and one Stripe mode: sales by treatment (net, IVA, gross, credits), refunds and chargebacks, the purchased-credit roll-forward at the price paid (opening deferred balance, purchased, consumed, returned, refunded, expired, charged back, adjusted, closing), free-credit movements, the orders, and every document of the month or still to issue with full fiscal data and the series; checks (paid orders without invoice, refunds without rectifying invoice, documents to issue, provider errors, closing balance against the lots). Reconciled to Stripe balance transactions (payments and refunds by charge, refund or PaymentIntent; fees, net and payouts totalled).
- **Rollback:** `db/rollbacks/092_billing_invoices_down.sql` refuses once any document exists; repair forward.

## Billing: Customer Screens, Run Estimate, Caps and Alerts

Launch L-15 (spec v2 §6.7, §6.10, §6.12; P-13, P-16; migration 109 for the lifecycle cohort only). Customers see their credits, buy them, set limits and see the estimate before every run.

- **Who sees billing (`lib/billing/billing-ui.ts`):** every customer-visible billing surface needs `BILLING_UI_ENABLED=true` (server-read, default off; the screens' kill switch) and `BILLING_CREDITS_ENABLED=true`, **and** an eligible workspace: `PLANS_V2_ENABLED` (Gate B), or its admin override `plans_v2` or `live_payments` (L-14), or `BILLING_TEST_WORKSPACE_IDS` (Stripe test mode). Before Gate B only allowlisted and internal test workspaces see balances or top-ups. Within one: owners everything, editors and Caudals operators the balance and usage, viewers nothing; platform admins read for support (audited). Every rule is server-side: the APIs answer 404 otherwise, and the shell (`features.billing`) never asks for viewers.
- **APIs (`lib/billing/customer-api.ts`):** `GET /billing/summary` (balance, plan, usage this month against the cap, alerts, next expiry; auto-recharge, card and payments for owners), `GET /billing/usage?from&to[&format=csv]` (by UTC day, by evaluation and run, by model and meter; CSV of every debit to the micro-credit), `GET /billing/ledger?cursor=` (owners; holds and releases only with `holds=1`; no reasons or actors), `GET/PUT /billing/caps` (PUT owners with an `Idempotency-Key`, audited by `billing.set_spend_cap`), `GET /billing/rates?evaluationId=` (the models a run uses with their credit rates, and the price list). `POST /billing/estimates` (L-10) also serves editors of eligible workspaces under `BILLING_ESTIMATES_ENABLED=operators` and returns the run gate.
- **Every number from the ledger (`lib/billing/account-view.ts`):** usage is the sum of debit entries (capture: engine tokens; action: platform meters) minus the entries that reverse them (run refunds, reversals), counted on the debit's day; balances are the account row the nightly verifier proves equal to the entries. Amounts travel as µcr strings; screens cut credits to two decimals (never overstating a balance), the CSV keeps six. Tested against independent SQL sums (`tests/billing/billing-ui-db.test.ts`).
- **Run gate (§6.7):** a run starts when available credits cover the p90 estimate, or auto-recharge covers the gap (on, saved card for the mode, not failing, within its monthly count and euros, payments open, one pack ≥ the gap: `lib/billing/limits.ts autoRechargeCover`). `admitRun` (enforce mode, credit workspaces) applies the same rule and also refuses with `409 CAP_REACHED` a run whose p90 would pass the monthly cap or a fixed per-run cap (at resume: the run's spend so far plus the p90 left). Contract workspaces are never gated.
- **Caps (`billing.spend_cap`, L-12 table):** monthly (this UTC month's usage plus open holds; none by default) and per run (a fixed cap, or a multiple of the run's p90, 2 × by default). Worker roles cannot read `spend_cap`, so caps are enforced at admission and by the scheduler's **billing watch** (`lib/billing/watch.ts`, every minute per workspace while credits are on, enforce mode only): a reached monthly cap pauses every queued or running run, a run at its own cap pauses, both with `cap_reached` (L-11's pause path). Grading and report passes already under way finish; test-set preparation is not stopped; overshoot is bounded by the calls in flight in that minute.
- **Alerts (billing watch, only where billing shows and the account ever had credits):** low balance (below 500 credits, or 20 % of the last pack; once per refill), the monthly cap at 50/80/100 % (once each per month), credits expiring in 30 and 7 days (per lot, not the monthly allowance), unusual spend (yesterday above 3 × the 28-day daily average and ≥ 100 credits; in the app only) and auto-recharge succeeded. Each is claimed once in `billing.alert_state`, written as an `evals.notification` (category `billing`; viewers never see it; payment notices are owners' only) and emailed with L-07's templates to owners who keep billing email on, in their language. Stripe test mode emails only Caudals' own addresses.
- **After credits arrive:** a paid top-up or auto-recharge resumes the workspace's work paused for `credits_exhausted` (never `cap_reached`) in its own transaction after the purchase commits (`resumeAfterCredits`).
- **Screens:** the shell's `BillingProvider` (`components/evals/billing-state.tsx`) loads the summary once per workspace and refreshes it every minute, on focus, every 4 s while a top-up is pending and on `caudals:billing-changed` (fired when the return page sees the order paid), so the sidebar pill, banner and Billing update without a reload. Settings → Billing and usage (`workspace-billing.tsx`), the run estimate dialog (`run-estimate-dialog.tsx`), the paused-for-credits panel and the one-step top-up (`billing-top-up.tsx` `TopUpDialog`) are described in docs/FRONTEND.md.
- **Lifecycle email (migration 109):** the L-07 cohort now includes self-serve workspaces on the pay-as-you-go plan, so a first purchase no longer drops a workspace out of the sequence.
## Billing: Bring your own provider key (BYOK)

Launch L-27 (spec v2 §6.11, D-11, invariant INV-11; migration 102 `billing_byok`). Flag `BYOK_ENABLED` (every eligible workspace) or the allowlist `BYOK_WORKSPACE_IDS` (design partners first), both read by the app at request time; default off.

- **Who and what:** owners (and platform admins for support) of workspaces on pay as you go, managed or partner plans connect an OpenAI, Anthropic, Google, Mistral or OpenRouter key in Settings → AI models and point engine roles (context analyzer, generator, judge, report writer) at a model on it. Free workspaces are refused by the API and by the database (`BYOK_PLAN_REQUIRED`). Adding or replacing a key needs a sign-in within 15 minutes; removing never does, and works even after the flag is switched off.
- **Workspace scope:** `evals.provider_account`, `provider_revision` and `provider_connection` carry `org_id` (NULL for Caudals' own providers). A trigger stamps a revision's and a connection's `org_id` from the account and never lets it change. The connection keeps the provider, a per-save `key_version`, the key's last state (`valid`, `quota_exceeded`, `invalid`), the model ids the key could list and revocation fields; it stores no part of the key in clear (no hint). Endpoints are fixed per provider (`evals.byok_endpoint`); nobody types an address.
- **Isolation:** row-level security on `provider_connection` — the admin login sees platform rows only, the inference worker platform rows plus the current workspace's own, and the web runtime has no grant at all. Writes and reads for owners go through `SECURITY DEFINER` functions (`evals.byok_connect`, `byok_rotate`, `byok_revoke`, `byok_set_route`, `byok_clear_route`, `byok_connections`, `byok_routes`; owner or platform admin of the workspace in scope) that never return the envelope. The web process checks the key with the provider's free calls (model list, or OpenRouter's key status) and encrypts it (`lib/evals/repositories/byok.ts`); only the inference worker decrypts it, for a reserved attempt of the same workspace (`connectionInvocationSecret` → `customerKeyInvocationSecret`), with the envelope bound to workspace, account and key version. The route guard (`evals.assert_route_priced`) lets a BYOK revision serve only its own workspace's workspace and evaluation routes, never the platform default; `loadProvider` refuses any step that names another workspace's revision (`provider_scope_denied`).
- **Routing:** `evals.byok_set_route` registers (or reuses) a workspace-scoped revision with a €0 price revision and upserts the workspace routes, keeping each role's web research where the model can search. Runs and generation jobs freeze it as before (migration 078). Reports record `methodology.data_routing` (`customer_provider`, `approved_providers` or `local_only`) from the judge and report-writer routes the run froze, shown in the web report, PDF and Word.
- **Failures (INV-11):** a provider failure on a BYOK revision becomes a `customer_key_*` reason (`invalid`, `quota`, `revoked`, `model`, `rate_limited`, `unavailable`, `rejected`); the worker records the key's state (`evals.byok_report`), pauses the whole workflow with the reason (L-11's pause path) and never moves the work to a Caudals key. A rejected or removed key stops later calls before any reservation. Judge and narrative jobs wait rather than fail; the run page and test-set preparation show "Your provider key failed: <reason>" with a link to Settings → AI models. Saving a working key (connect or replace) resumes the paused work by itself (`resumeKeyPausedWork`, retry backoff cleared). Removing a key erases the envelope, retires its revisions and deletes the workspace's routes to it in one transaction, so new work uses Caudals' models only by the owner's choice; work already frozen on the key pauses with `customer_key_revoked`. A workspace deletion erases its keys (`evals.byok_revoke_for_deletion`).
- **Billing (§6.3, §6.8):** `billing.provider_revision_rate_key` reports a BYOK revision as free of token credits, so holds, captures, shadow entries, the shadow diff and the estimator (which labels the role "your key") charge 0 for its calls in shadow and enforce modes; platform meters (questions, graded answers, pages, searches) are charged as usual. Our euro liability is 0 (price €0, account ceiling 0).
- **Flag off:** no new keys or model choices (404); existing keys keep serving their workspace until the owner removes them (no silent switch). Rollback `db/rollbacks/102_billing_byok_down.sql` refuses once any workspace provider row exists; repair forward.

## Billing: Ops Console, Two-person Approvals and Reconciliation

Launch L-16 (spec v2 §6.4, §6.9, §6.13, §6.15, P-49; migration 094). Operator-only: platform admins, a sign-in within 15 minutes for every change, a reason, an `Idempotency-Key`, and an `evals.audit_event` with before and after values.

- **Console (`/ops/platform/billing`, `components/evals/ops-billing*.tsx`):** account search and view (ledger timeline, lots, holds, orders, invoices and rectifying invoices, alerts, approvals, override, the §6.9 invariants; the read is an audited support access), approvals, price book, reconciliation, manual invoices (L-13's attach and void), the monthly accountant export (L-13's), the fraud queue and per-workspace overrides (L-14's API). Platform · Usage and budgets lists credits sold, granted, consumed, held, expired and the shadow charges per workspace (also for platform operators); the run inspector shows credits held and charged next to our cost per engine attempt; Providers & models links its €0 warning to the price book.
- **Actions (`lib/billing/ops.ts`, `/api/evals/v1/billing/admin/{grants,adjustments,credit-refunds,refunds,expiry,freeze}`):** grant (amount, reason, expiry, campaign tag; L-09 `billing.grant`), adjust ± (`billing.adjust`), refund credits (a run's unreversed charges with `billing.refund_run`, or one entry with `billing.reverse`), refund money for an untouched purchase within 14 days (L-12's ledger-then-Stripe path), extend a lot's expiry (`billing.extend_lot_expiry`: later only, unexpired lots with credits left; no credit moves, so no ledger entry) and freeze or unfreeze (`billing.set_account_freeze`; unfreezing waits for an open dispute to close). Each writes its entries and audit event in one transaction; a replay of the same key answers the same.
- **Two-person rule (`billing.approval_request`):** above 10,000 credits (€100), or a money refund above €100 net, the action opens a request instead of running: workspace, action, the resolved payload (expiry dates fixed at request time) and its SHA-256, requester, 24-hour expiry. A different platform admin approves the payload hash they reviewed (`billing.approve_request`, `APPROVER_MUST_DIFFER` for the requester, `APPROVAL_PAYLOAD_MISMATCH`, `APPROVAL_EXPIRED`); the action then runs as the approver in that transaction with the key `approval:<id>`, and `billing.complete_approval` records the result. A money refund approves, removes the credits, refunds in Stripe and closes the request (the same approver can retry if Stripe did not confirm). The requester cancels, another admin rejects (`billing.close_approval`). Backstop: a `BEFORE INSERT` trigger on `billing.ledger_entry` refuses a grant, bonus, allowance, adjustment, reversal or refund above the threshold written by a person unless the transaction carries an approval this person approved for this workspace (`SECOND_APPROVER_REQUIRED`); services (allowance, purchases, webhooks) are not affected.
- **Price notices (`lib/billing/price-notice.ts`):** a revision that raises any rate takes effect only when `notice_sent_at ≤ effective_at − 30 days` (`billing.price_notice_ok`): `billing.price_book_at`, the hourly activation and manual activation (`NOTICE_NOT_SENT`) skip it, and a held revision can go back to draft after its date. `billing.record_price_notice` records the notice once, only for scheduled raising revisions and never after the deadline (`NOTICE_TOO_LATE`), and writes the in-app notice (`price_increase`) to each recipient workspace. `billing.price_notice_recipients` lists credit workspaces (not contract, not deleted) whose completed engine calls used a raised model in the last 90 days (any run when a meter rises), with their owners. Email (`price_increase` template, EN/ES, essential) goes to owners only while `BILLING_PRICE_NOTICES=owners`; the default `internal` sends test copies to the internal address and refuses the real send. Decreases apply at once (schedule today).
- **Daily reconciliation (`lib/billing/reconcile.ts`, evals scheduler at 05:00 UTC for the previous UTC day and at start; `POST /admin/reconciliation` on demand):** `billing.reconciliation_checks(day, livemode)` compares paid orders with their purchase and bonus entries, purchase entries with paid orders, refunded orders with their refund (or mirrored adjustment) entries, refund entries with refunded orders, unconfirmed refunds, chargebacks, invoices and rectifying invoices against the orders' amounts, documents without an order, holds open over 25 hours, the account invariants and the shadow diff. The application adds Stripe: the day's balance transactions (an hour either side) matched to the day's payments and refunds with the export's matcher; unmatched Stripe payments are looked up by PaymentIntent (Checkout metadata names the order) — a payment whose order never got credits is a difference, one settled on another day or not ours is an explained note; Stripe not readable counts as a difference. Reports are append-only in `billing.reconciliation_report`; `billing_reconciliation` and `price_notice_due` alerts come from `scripts/evals/health-alerts.sh` (runbook 23).
- **Reads:** `billing.search_accounts`, `billing.credit_usage(from, to)`, `billing.fraud_queue(days)` (free sign-ups with 3+ sites in 30 days, 3+ runs in a day or a shared company domain; 3+ top-ups in 24 h or repeated failed payments; orders with risk flags; disputes; frozen accounts), `billing.orders_lookup`, `billing.list_approvals`, `billing.reconciliation_reports`.
- **Rollback:** `db/rollbacks/094_billing_approvals_down.sql` restores L-10's price-book functions and refuses once an approval, a reconciliation report or a recorded notice exists; repair forward.

## Partner Accounts and Referral Codes

Launch L-28 (spec v2 P-52, §6.5 "Partner", §6.15, §7.8; migration 103). Agencies and integrators manage several client workspaces from one account and earn on referrals. Behind `PARTNERS_ENABLED` (server-read, default off): `true` opens every partner ops onboarded by hand; a comma-separated list of partner ids opens only those (the per-partner gate); `admins` opens only the ops API. Off, every partner page and route answers 404 and identity reads nothing partner-related.

- **Data (`evals` schema):** `partner` (agreement: name, status `active`/`suspended`/`closed`, revenue share in basis points, 20 % by default; client cap; optional logo), `partner_member` (`admin` | `member`), `partner_client` (one live link per workspace; `created` by the partner with access `manage`, or `linked` by ops, access `work` unless ops choose `manage`), `partner_referral_code` (`cp-` + 10 hex, unique, revocable), `partner_referral` (one referring partner per workspace, with its first paid order), `partner_allowance` (credits per Madrid month per agreement) and `partner_allowance_grant`. RLS: partner members read their own partner's rows, platform admins all, a client's own members see their workspace's link; nobody writes the tables directly. Every write is a SECURITY DEFINER function that checks the actor in the database (`evals._partner_require`, `evals._partner_admin`) and is audited (partner-level events have no workspace; client-level events are in the client's audit trail).
- **Partner scope, operator client model:** partner people reach clients through ordinary membership rows marked `membership.partner_id`, kept in step by `evals._partner_sync` in the same transaction as every change (person added or removed, client linked or unlinked, partner suspended or closed). Partner admins are `owner` of clients the partner manages (`manage`), everyone else `editor`; never the workspace `operator` role, so they are never platform staff (`isPlatformStaff` false, no readout notes, operator estimates, recipe authority or `/ops`). A person's own membership in a workspace is never changed by a partner. `requireWorkspace`, the switcher and every tenant policy work unchanged. Partner people do not count against a member cap (093's `enforce_plan_members` and `plan_usage` skip them). `identity.partners` lists the person's active partners the flag opens (display only; routes re-check in SQL).
- **Clients:** `evals.partner_create_client` (partner admins; idempotent per request key) makes a workspace on the `partner` plan (credits billing; PAYG-sized limits until ops set the agreement's; no member cap). `partner_link_client` / `partner_unlink_client` are ops-only with a reason; unlinking or closing is refused while a managed client would be left without an owner of its own (`PARTNER_CLIENT_ORPHAN`, `PARTNER_CLIENTS_ACTIVE`), and the last partner admin cannot leave then (`PARTNER_LAST_ADMIN`).
- **Referral attribution (L-02 first touch):** partner links carry `utm_source=partner&utm_medium=referral&partner=<code>` to `caudals.com/{en,es}/demo` and `app.caudals.com/workspace/start`. The code travels in the consented first-touch cookie to the demo run, the sign-up and `workspace.acquisition_attribution`; a trigger on `evals.workspace` matches `partner` (then `ref`) against a live code of an active partner and records `partner_referral` (`attributed_via signup`). A trigger on `billing.top_up_order` records the first paid order (`first_paid_*`) and, if the workspace's first touch names a code issued after sign-up, attributes it then (`payment`). Both triggers swallow their own errors: attribution never fails a sign-up or a payment. Revoking a code stops new attributions; earlier ones stay. Visitors who refuse optional cookies are not attributed (decision left to the founder).
- **Referred revenue and the statement:** `evals.partner_referrals(partner, livemode)` sums net euros of a referred workspace's paid top-ups within a year of its first payment in that Stripe mode, without refunded or charged-back orders; NULL (never 0) until it has paid. `evals.partner_statement(partner, month, livemode)` returns, for a Madrid calendar month: each first-year referred payment (net and the share at the partner's rate), each refund or chargeback of one (negative), each allowance grant (ledger amount) and each client's credit use while linked (capture and action entries, minus the refunds and reversals of those entries). `GET /api/evals/v1/partners/:id/statement?month=&mode=` renders it as CSV (`lib/evals/partners/statement.ts`: formula-safe text, plain numbers, totals including the credit equivalent at 100 credits per euro). Payouts are manual.
- **Allowance (§6.15 "ops may move credits for partners"):** `evals.partner_grant_allowance` (platform admins, in the client's scope, Idempotency-Key) is a `billing.grant` (source `contract_allowance`, campaign `partner_allowance`, ref `partner`) into one live client, never above the month's allowance (`PARTNER_ALLOWANCE_EXCEEDED`), expiring at the end of the next month by default.
- **White-label PDFs:** a partner admin uploads a PNG or JPEG (≤ 512 KB, 16–4,096 px a side, recognised from its bytes) to private storage `evals/partners/<partner>/logo/<uuid>`. `queuePdfExport` asks `evals.partner_pdf_brand(org)` (the live link, active partner, logo set, partner open under the flag) and stores `{partner_id, logo_sha256}` on the export job (`export_job.brand`, checked shape, never on share jobs); the branded file's path ends `.v<layout>.b<sha8>.pdf`, so a new or removed logo renders a fresh copy. The documents worker reads the logo only through `evals.partner_pdf_logo(org, partner, sha)` (its one partner grant), which re-checks the link and the hash; a forged or stale brand renders no logo. The cover keeps the Caudals brand bar and adds "Delivered by <partner>" with the logo and "Evaluation and methodology by Caudals" (`ReportDocumentOptions.partner`). Share PDFs, Word and readout decks are unbranded.
- **APIs (`app/api/evals/v1/partners/*`, `lib/evals/partners/repository.ts`):** `GET/POST /partners`, `GET/PATCH /partners/:id`, `POST/DELETE /partners/:id/members`, `POST/DELETE /partners/:id/clients`, `POST/DELETE /partners/:id/codes`, `GET/PUT/DELETE /partners/:id/logo`, `PUT/POST /partners/:id/allowance`, `GET /partners/:id/statement`. Ops changes need a platform admin signed in within 15 minutes and a reason; database codes map to 404 (scope) or 409/422 with a message. A platform admin's read of a partner is audited (`support.partner_read`).
- **Rollback:** `db/rollbacks/103_evals_partners_down.sql` refuses once a partner, a partner membership or a branded export exists; repair forward.

## Earlier Evaluation Architecture Sketch (superseded)

This sketch predates the staged implementation above. Its `/proof`, `/e/[projectId]`, and `lib/eval` paths are not the current evaluation-product contract. The product specification and `docs/evals/AGENTS.md` take precedence.

### Phase 0 — manual delivery

- Suite in a spreadsheet, exported as CSV.
- A runner script of roughly 150 lines calls the target and writes results JSONL.
- Grading: deterministic checks, an LLM judge and two human reviewers.
- Analysis in spreadsheet pivots (cause × topic × tier); the report is written as HTML and rendered to PDF with brand tokens.
- Expert work runs in shared spreadsheets under documented provenance and access rules.

### Phase 1 — in-app product

```
app/(eval)/proof/              public self-serve demo, no signup
app/(eval)/e/[projectId]/      customer dashboard (magic link): runs, cases, report
app/(evaluation)/(authenticated)/  workspace, operations and expert pages in a persistent shell
lib/eval/targets/              adapters: http, openai-compatible, widget, manual, self-run import
lib/eval/graders/              deterministic checks, LLM judge, human queue
lib/eval/runner.ts             queue consumer
lib/eval/report.ts             report data assembly
```

Eight domain tables in the existing PostgreSQL, with RLS by `org_id`, plus an `eval_job` queue table:

| Table | Purpose |
| --- | --- |
| `eval_project` | Customer engagement: org, sector, locale, status |
| `eval_target` | System under test: kind (`http`, `openai`, `widget`, `manual`, `self_run`), config, auth reference, rate limit, label |
| `eval_case` | Versioned case: source, tier, scope, author, reviewer, sign-off |
| `eval_run` | One execution: target, suite version, timings, model fingerprint, summary |
| `eval_result` | One row per case per run: response, retrieved context, latency, tokens, cost, score, grounded/confident/refused, grader, rationale, cause |
| `eval_review` | Human override of a result; always wins |
| `eval_finding` | Report finding: severity, category, body, linked cases |
| `eval_report` | Report version, PDF object key, publish time, share token |

Invariants:

- `eval_result` rows are immutable once a run completes; corrections go to `eval_review`.
- Suite versions are frozen per run; judge model versions are pinned per suite version.
- Every run stores a `model_fingerprint`.
- Customer content is redacted at ingest and processed on EU infrastructure.

Runner and integrations:

- One Node worker on the VPS consumes `eval_job` with `FOR UPDATE SKIP LOCKED`. It deliberately does not use Temporal or Dagster: a run is a few hundred HTTP calls.
- Per-target rate limits (default 6 requests/minute with jitter against third-party production), three retries with exponential backoff, timeouts recorded as results.
- Self-run probe: a packaged CLI/container that executes a frozen suite inside the customer's network and emits a signed results JSONL for import, so Caudals never holds production credentials.
- Provider layer: at least two model providers behind a thin abstraction (judge ensembling, vendor-swap detection); tokens and cost logged per result.
- Case deduplication by embedding similarity uses pgvector in the existing database; no separate vector service.

`/proof` demo: a public documentation URL or PDF (≤10 MB, 30 pages) → 12 cited test questions → answers from the visitor's endpoint, pasted manually, or from a baseline model → scorecard with failing cases → offer of a Reality Check. IP rate limits, 24-hour content retention, daily model-spend cap.

Reports are assembled from run data, rendered HTML → PDF, and stored in object storage with run archives and JSONL exports.

Expert work: freelance domain experts get restricted accounts to author and review cases and dataset items. Access is scoped to the redacted material of their assigned tasks, and every item records author, reviewer and guideline version. Expert, task and dataset-item tables are added when custom dataset builds move in-app.

  data, the legacy CLI and frozen operator/supplier modules.
- Dagster, Temporal, Marquez and lakeFS keep dedicated databases inside
  `caudals-postgres`; those databases, the stacks' named volumes and their
  Docker secrets are retained.
- `npm run platform:completion-status` checks their readiness and the legacy
  dataset-build evidence only with `CAUDALS_LEGACY_STACKS_GATE_ENABLED=true`.
  CI no longer builds or deploys Dagster. Deploy scripts remain one-command
  restores.

Runbook details, secrets and dashboard ports are in `docs/TOOLS.md` → Legacy Private Stacks.
- **Sector packs and monthly new questions (launch L-25, migration 100, `SECTOR_PACKS_ENABLED`).** Sector packs are platform data outside every workspace: `evals.sector_pack` (sector, jurisdiction, language, EN/ES title and summary, the domain pack it reuses: `generic-grounded-qa`), `evals.sector_pack_version` (`draft` → `in_review` → `published`, at most one open version per pack) and `evals.sector_pack_item` (question, expected answer, key facts, severity; the cited source's URL, title, publisher, locator, verbatim excerpt and retrieval date (freshness); rights `public_official_text`, `public_sector_reuse`, `licensed` with a licence reference, or `caudals_owned`, with the basis; author, last editor and the reviewing Stage E expert profile; a database content hash). Constraints: every item is `scope = 'sector_generic'`; customer-owned rights are not a valid kind; the writer functions refuse inside a workspace context (`evals.org_id()` set) and any payload naming a workspace or case; one question fingerprint per version (deduplication). A published version and its items are immutable (triggers, even for the table owner); publication needs at least one item, every item `approved` by an eligible expert with reviewer, profile and time recorded (trigger), and the app requires 60 (`SECTOR_PACK_MIN_PUBLISHED_ITEMS`). Reviews are recorded only by an eligible, verified expert who is neither the author nor the last editor; an edit resets the review. RLS: staff and verified experts read every version, everyone else only published ones; the runtime role has SELECT only and every write goes through SECURITY DEFINER functions (`sector_pack_save`, `_version_open` (copies the newest published version with its reviews), `_item_save`, `_item_remove`, `_item_review`, `_version_transition`), each audited in `evals.audit_event` with a NULL workspace. `lib/evals/sector-packs/` holds the import schema and validation (`schema.ts`), the repository (`store.ts`), the monthly job (`refresh.ts`) and the shared "append questions as a new version" helper (`suite-append.ts`). Authoring is the ops library's **Sector packs** tab (`/ops/library/sector-packs`, staff: import, submit, return, publish, edit) and `/review/sector-packs` (verified experts: draft and edit; eligible experts: approve, request changes, reject). APIs: `GET/POST /api/evals/v1/sector-packs`, `POST …/sector-packs/versions`, `GET …/versions/:id`, `POST …/versions/:id/status`, `POST …/versions/:id/items`, `DELETE …/items/:id`, `POST …/items/:id/review`. Customers: `GET/POST /api/evals/v1/suites/:id/sector-questions` suggests and adds the newest **published** version for the workspace's sector (`evals.workspace_library_setting.sector`, `PUT /api/evals/v1/workspace/library-settings`): the pack becomes a frozen source of the project (one excerpt per item with its citation line, stored privately for 12 months, `caudals.evals/sector-pack-source`), each missing question a new case modelled on the set's first question (same rubric and graders) with provenance `human_authored`, `expert_reviewed` with the reviewer, rights mapped (`public_official_text` → `public_domain`, the others → `licensed`/`caudals_owned`), tags `sector_generic` and the extension `caudals.evals/sector-pack` (pack, version, item, source, rights, reviewer). It writes the next draft version; a set whose newest version was frozen is frozen again as a new version. `evals.sector_pack_case_link` records each case revision's item (only published items, trigger); `evals.sector_pack_item_stats(version)` aggregates outcomes per item key across workspaces (counts only, outcome counts withheld below three workspaces). The plan's question cap applies (`PLAN_LIMIT_QUESTIONS` with plans v2, else the generic `PLAN_LIMIT`).
- **Monthly new questions (P-26).** Opt-in per workspace (`workspace_library_setting.monthly_questions`; owners and operators; managed, PAYG and partner plans). Every five minutes the scheduler (with `SECTOR_PACKS_ENABLED`) lists opted-in workspaces (`evals.monthly_questions_due()`, scheduler role only) and, once per source and calendar month (`evals.source_refresh`, unique per source and period), queues a new `website_source_job` for each live website source of an evaluation with an approved test set whose last reading predates the month (same start page, page limit and L-34 page selection; at most 10 sources a month): the existing browser reader, egress proxy and document worker produce a new source revision (its file path carries the job id). The new revision is compared page by page (`Source URL:` blocks, a hash of letters and digits only) with the previous one; excerpts of new and changed pages go to one generator call on the evaluation's generation route through the reservation path (workspace and refresh budgets, credit holds; `refreshJobId` gives it the generation deadline), with the draft prompt, the set's questions to avoid, and at most 12 questions per source and 25 per workspace and month. Returned questions are validated against those excerpts by the generation validator and saved as `evals.question_proposal` rows (immutable once decided). Owners, editors and operators approve proposals into a new test-set version (cases `synthetic` with the generator and prompt revision, extension `caudals.evals/monthly-proposal` with refresh, page and approver) or reject them (`evals.decide_question_proposal`, audited); the test set page shows them (`GET/POST /api/evals/v1/suites/:id/proposals`). Re-reading pages is metered like any website reading.

## Security and Reliability Anchors

- RLS-first access model with scoped service-role usage
- Durable abuse controls on public APIs
- Webhook replay/idempotency protections when payment code is active
- Upload/path validation guardrails
- Provenance and auditability for every case, run, review, report and dataset item; results are immutable
- Customer content: PII redacted at ingest, EU processing, named sub-processors, retention and deletion per data handling policies
- Freelance experts: least-privilege access to redacted task material only
- No adversarial inputs against any system without its owner's written authorisation
- Error capture and opt-in stdout tracing without default PII transmission
- CI quality gates for release confidence

## Core Lifecycle Flows

1. Demand capture: a visitor reads the landing page, blog or newsletter → contacts us, books a call or runs the free `/demo` (and may open a free account from it) → operators qualify the opportunity in the Leads CRM.
2. Reality Check: operators pick a qualifying public system → run a 40-case probe under the rules of engagement → send a teaser → deliver the free report and readout.
3. Pilot or Full Evaluation: kickoff → documents, real questions and expert session → suite authored and signed off → runs (hosted, self-run or output-only) → grading and review → report, live readout and JSONL export.
4. Subscription: monthly (or weekly) runs → new cases and new data, including expert-authored cases → regression report.
5. Custom dataset build: coverage gaps and failure causes scope the dataset → freelance domain experts build it under Caudals guidelines and double review → dataset with provenance and QA scorecard → a re-run proves the score moved.
