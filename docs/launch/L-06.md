## What shipped

- **Automatic start for demo sign-ups (P-01).** The demo import already queues the connection check and the reading of the demo's site (capped at 25 pages, no model calls). The sign-up now records an intent in `evals.onboarding_autostart`, and generation starts by itself, up to the plan's test limit (`max_tests_per_set`, 50 on the free plan), with the Prepare page's prompt revision, as soon as the site has text and the connection check does not say "unreachable".
  - "Run the connection check first" applies to the costly part: no generation (DGX time) starts while the chat or API is unreachable (`failed`, or `destination_*`/`connection_unsupported`) or the site could not be read. Site reading itself (no model calls) runs alongside the check, as before.
  - A chat that only needs help to automate (`recipe_not_found`, CAPTCHA, login) does not block the test set: the questions come from the pages, and the page shows the chat guidance and "Get help". Blocked intents are re-checked every 10 s for two days, so a fix resumes them. A check still queued after five minutes no longer holds the start.
  - Exactly one job: the intent row is locked `FOR UPDATE`, the start runs inside a savepoint with the fixed key `onboarding-autostart-<evaluation>`, on behalf of the person who signed up (access rechecked, as for restarts). A job started by hand supersedes the intent.
  - Advanced from three places: once right after sign-up, by every read of `GET /api/evals/v1/evaluations/:id/onboarding` (the evaluation page polls it every 4 s while anything moves) and by a new 10-second onboarding tick in the scheduler (`evals.onboarding_autostart_due()` lists only workspaces with pending intents).
  - Workers now discover new workspaces every 10 s instead of 30 s (`lib/evals/queue/workspaces.ts`), so a new sign-up's site is read within seconds.
- **First evaluation panel (P-01).** A four-step checklist on the evaluation page (check the connection, read your pages, write the test set, run and read the results) with live status and typical ranges measured in production on 2026-10-12: site reading 1–3 min, test set 5–35 min (p25–p90 for ≤ 50 questions), run 30–90 min (website chats, p50 37–61 min), plus "typical ranges, not promises". A "What happens next" panel. While the start waits, Prepare replaces its Generate button with "Caudals starts writing up to N questions by itself". A demo imported without a system (curl-style APIs) says so instead of asking for a key (fix `19264c3`, found in the drill).
- **Recovery and Get help.** The panel shows the demo's recovery guidance (same wording, plus the in-app step) and "Get help": one ops task per evaluation (`evals.onboarding_help_request`, audited), one email to the operators at `COLLABORATION_NOTIFICATION_EMAIL` (workspace and evaluation names, reason code, links; Resend idempotency key per request), listed in Ops → Growth → Help requests with Resolve (operator role checked in SQL).
- **Activation checklist (P-02).** Connect a system, add reference pages, run, read results, invite a colleague; computed from real state by `evals.workspace_onboarding_state` ("read results" is recorded when a member opens a published report). Persisted per workspace, dismissable by writers, shown on the evaluations list for workspaces created through self-serve sign-up. Empty states always show it (no hide) and replace "ask an owner" for viewers.
- **Two-question welcome (P-04).** For the owner after the first sign-in: system type (website chat, API assistant, internal assistant, agent, other) and goal (check before launch, monitor changes, compare vendors, evidence for an AI review). Optional chips, "Save answers" or "Skip"; never blocks. Stored on the workspace, shown per new account in `/ops/growth` ("Says it tests", "Goal (welcome)").
- **Ops growth.** Beside L-21's v2 table: the two welcome columns, a weekly table "Demo sign-ups reaching a test set within 30 minutes" (P-01's ≥ 60 % target, from `account_created` with acquisition `demo` and the first `test_set_ready`), and help requests with Resolve.
- **Sign-up page.** A "What happens next" line (demo: the demo is imported and the full test set starts preparing; direct: a checklist guides you) and a live password strength hint (length first, then variety; the server still requires 12 characters).
- **Events.** None added: `test_set_ready` already comes from the real generation path (`evaluation-generation/*`) with its duration; `account_created` and `evaluation_created` are unchanged.
- **Example evaluation (L-33).** Wired at the rebase onto L-33: the empty states link `/workspace/example` through L-33's `ExampleEvaluationLink` (the action for viewers, a text link under "New evaluation" for writers), and the activation checklist card links it too. Both render nothing while `EXAMPLE_EVALUATION_ENABLED` is off or the example is hidden.
- **Example hide choice moved to the workspace (L-33 follow-up).** L-33 kept "hide the example" on the owner's device (`localStorage`). It is now `evals.workspace_onboarding.example_hidden_at`, set by owners and operators through `PATCH /api/evals/v1/workspace/onboarding` (`hide_example`/`show_example`, gated by `EXAMPLE_EVALUATION_ENABLED`, role checked in SQL, audited `workspace.example_hidden`/`shown`). It works in every workspace: hiding creates the row with `tracked = false`, so an ops-created pilot never gets the checklist or welcome. `useExampleEvaluation` reads and writes it through `components/evals/workspace-onboarding-store.ts` (one shared copy with the checklist); the device storage is gone and the copy says "for everyone in this workspace". L-33's hide contract now asserts the PATCH calls and an empty `localStorage`.

## Risks and notes

- Demos of curl-style APIs (`https_json`) import no system, so the first run prepares the test set but the person must add the system before running. Importing such systems is a follow-up for the import (out of L-06's scope).
- Workspace deletion leaves an active generation job row for a deleted workspace (pre-existing behaviour; workers stop serving it). A follow-up could stop jobs and resolve open help requests on deletion.
- Help requests stay visible for deleted workspaces until an operator resolves them.
- The time ranges are constants from 2026-10-12 production data; revisit when L-18/L-24 change throughput.
- Three platform alert emails went out during the deploy window (the health timer runs every ten minutes while workers restarted); afterwards only the existing `unresolved_attempts` alert remained open.
