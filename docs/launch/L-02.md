# L-02 · Funnel events and growth dashboard v1

Status: **done** — deployed and verified in production on 2026-10-12 (`144510e`, fix `cf8252b`).

## Implementation

- One event catalogue in `lib/analytics/events.ts`, with disjoint client/server names and per-event property allowlists. Legacy funnel/dashboard event names and their unused tracker are removed. Paths are route templates; email, IP addresses, arbitrary properties and non-finite numeric values are rejected. Run/revision correlation and retry keys are hashed; user IDs and emails are not written.
- Client events require optional-cookie consent and the runtime `ANALYTICS_EVENTS_V2` flag. Ingestion requires explicit consent, same origin, a bounded body and a pseudonymous rate-limit key. The root tracker observes client navigation, including consent granted after initial render. Umami mirrors queued, consented events when its script becomes ready; automatic unsanitized page tracking is disabled.
- First consented touch keeps sanitized UTM/ref/partner labels and the existing opaque Leads journey IDs in an optional first-party cookie for 90 days across marketing/app hosts. Withdrawal clears it and the session storage. A demo gets a sanitized snapshot; signup stores it on the workspace, reserved for L-12's first payment. Cookie Policy updated in EN/ES to version 2026-10-12. Link resolution and Leads' identity/revenue rules are unchanged.
- Migration 082 adds workspace/hash/attribution/deduplication dimensions, growth indexes and operator-only SELECT RLS. A bounded insert-only security-definer function handles conflict checks without exposing rows to customer or worker sessions. Domain emitters use the same transaction and savepoints; failures cannot roll back the domain write. Unique keys prevent replay/concurrent double counts.
- `/ops/growth` is gated by the runtime flag and platform operator/admin identity; SQL independently checks that role. Weekly event counts, eight-week demo outcomes, sources, newest 200 accounts and eight-week activity cohorts are served by one indexed query with a 1.5-second statement timeout. No personal names/emails or raw target URLs. EN/ES platform UI, keyboard-accessible scrollable tables and responsive layout.

## Event ownership and meaning

See the catalogue table in `docs/ARCHITECTURE.md`. Page/view/click events are consented; domain events record necessary product state transitions without browser identifiers. Run start means an accepted run, including queued work; completion follows grading/reporting or terminal cancellation. Test-set readiness means the set is ready for review/frozen, not that a human approved it. First report views are deduplicated per report revision, across authenticated/shared access; export downloads per artifact/revision and format. Cohorts count workspaces with a run start or first report view, not passive polling. Collection is prospective; no historical events are invented.

The catalogue reserves future features' emitters: example viewing L-33, customer expert-review request L-26, readout L-35, report questions L-36. Those packages must exercise their real workflows before the spec's all-events acceptance can pass. L-10/L-11 fill estimates/credits when billing hooks exist; unknown costs stay null, never zero. L-12 adds payment events and consumes the saved first-touch attribution. These are explicit remaining work in the overall goal, not simulated events in v1.
