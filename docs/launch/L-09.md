# L-09 · Billing core: credit ledger — handoff

Package ID / title: L-09 · Billing core: credit ledger (spec v2 §6.1, §6.2, §6.8–§6.10, §6.16, §6.18; §8.3)
Status: in_progress (draft; production verification pending)

## Implemented behaviour

An append-only, idempotent credit ledger that L-10, L-11, L-12, L-14, L-15 and L-16 build on. Deployed dark: nothing calls it on the run path yet.

- Unit: 1 credit = €0.01 excl. VAT, stored as micro-credits (µcr, 1 credit = 1,000,000) in `bigint` columns ending `_ucr`.
- Schema `billing` (migration 084): `credit_account`, `credit_lot`, `credit_hold`, `ledger_entry` (append-only trigger on UPDATE, DELETE and TRUNCATE), `verification_run`. RLS by `org_id`; runtime and worker roles read their scoped workspace's rows and cannot write any table.
- One account per workspace, backfilled at zero (`managed` → `contract`, `free` → `free`); a trigger on `evals.workspace_entitlement` creates accounts for new workspaces and keeps `billing_mode` in step with the plan (any other plan → `credits`).
- Nightly verifier in the evals scheduler (start-up and the 03:00 UTC hour) → `billing.verification_run` and a `billing_verified` / `billing_drift` log line. Hourly expiry when `BILLING_CREDITS_ENABLED=true`.
- Flags: `BILLING_CREDITS_ENABLED` (default `false`), `BILLING_ENFORCE` (`shadow` default | `enforce`), read on the server (`lib/billing/config.ts`), allow-listed in `scripts/set-app-credentials.sh`, and copied from the app credentials to the worker, scheduler, browser and document services by `scripts/deploy-evals-production.sh`.

## Function contracts (for L-10, L-11, L-12 and later)

All functions are `SECURITY DEFINER`, take the workspace as `p_org_id` (must equal the transaction's `evals.org_id`), write entries and balances in the caller's transaction, and are idempotent by key: a replay returns the original entry, a replay with different values raises `IDEMPOTENCY_CONFLICT`. Errors are raised as their code (`lib/billing/ledger.ts` maps them to `BillingError` / `CreditsExhausted`). Entry idempotency keys are `<function>:<key>` (`grant:`, `hold:`, `capture:`, `release:`, `action:`, `adjust:`, `reverse:`, `run-refund:<run>:<entry>`, `expiry:<lot>:<n>`).

| Function | TS wrapper | Who | Contract |
| --- | --- | --- | --- |
| `billing.grant(org, key, ucr, source, expires_at, reason?, campaign?, ref_kind?, ref_id?, request_id?) → ledger_entry` | `grantCredits` | platform admin (reason required, audited) or `service:`/`system:` actor | New lot. `source` ∈ grant, promo, bonus, allowance, contract_allowance (entry type grant/bonus/allowance). `expires_at` NULL = never; the wrapper defaults per D-10 when omitted |
| `billing.hold(org, key, ucr, expires_at?, run_id?, attempt_id?, case_unit_id?, price_book_revision_id?, request_id?) → ledger_entry` | `holdCredits` (`attemptHoldKey(id)` = `attempt:<id>`) | any tenant actor (runtime, workers) | Reserves unheld, unexpired credit oldest-expiring first; default hold expiry 24 h. `CREDITS_EXHAUSTED`, `ACCOUNT_FROZEN` |
| `billing.capture(org, key, ucr, request_id?, metadata?) → setof ledger_entry` | `captureCredits` → `{capture, release}` | any tenant actor | Charges min(ucr, hold) from the hold's lots in order, releases the rest; overage in metadata. 0 allowed. `HOLD_NOT_FOUND`, `HOLD_NOT_OPEN` (released or expired) |
| `billing.release(org, key, reason?, request_id?) → ledger_entry` | `releaseCredits` | any tenant actor | Releases the whole hold. Repeats (and releases of an expired hold) return the original release entry; a captured hold raises `HOLD_NOT_OPEN` |
| `billing.charge_action(org, key, meter, ucr, quantity=1, run_id?, case_unit_id?, price_book_revision_id?, allow_partial=false, request_id?) → ledger_entry` | `chargeAction` (`unitActionKey(id)` = `unit:<id>`) | any tenant actor | Platform meter for completed work. `CREDITS_EXHAUSTED` when short unless `allow_partial` (charges what is there; `shortfall_ucr` in metadata). Allowed on frozen accounts |
| `billing.adjust(org, key, signed ucr, reason, expires_at?, request_id?) → ledger_entry` | `adjustCredits` | admin or service; reason required; audited | + is a new `adjustment` lot; − consumes unheld credit |
| `billing.reverse(org, key, entry_id, reason, request_id?) → ledger_entry` | `reverseEntry` | admin or service; audited | Reversal against the same lots, once per entry. Credit entries need the credit still unheld in their lots (`REVERSAL_EXCEEDS_REMAINING`); debit entries (action, capture, −adjustment) return credit to their lots |
| `billing.refund_run(org, run_id, reason, request_id?) → setof ledger_entry` | `refundRun` | admin or service | Groundwork for L-11: one `refund` entry per unreversed capture and action of the run (key `run-refund:<run_id>`); a replay returns them |
| `billing.expire_due(org?, limit=100) → (org_id, holds_expired, lots_expired, expired_ucr)` | `expireDue` | admin or service | Expires holds past `expires_at` (state `expired`, release entry) then the unheld part of due lots |
| `billing.verify_account(org?) → rows with issues[]` | `verifyAccounts` | scoped workspace; all accounts for admin or service | §6.9 invariants; empty `issues` = consistent |
| `billing.record_verification() → verification_run` | `recordVerification` | admin or service | The nightly verifier |

Grants: hold, capture, release, charge_action and verify_account → `evals_runtime`, `evals_worker`, `evals_browser`, `evals_document` (also re-applied by `infra/evals/{worker,browser,document}-grants.sql`). grant, adjust, reverse, refund_run, expire_due and record_verification → `evals_runtime` only (the scheduler inherits it).

Lock order: provider account → workspace and run budgets → `billing.credit_account` → lots and holds. Call billing functions after `reserve()`/`settle()` in the same transaction. Every function locks the account row first and never touches evals budget rows.

Not built here (by design): `record_purchase` (L-12: needs `top_up_order`; use the internal `billing._credit` helper with source `purchase`, `unit_price_eur` and `order_id`), the price book (L-10; `price_book_revision_id` has no foreign key yet), engine hooks and shadow comparisons (L-11; `allocateOldestExpiringFirst` and `splitCapture` in `lib/billing/units.ts` model the database maths), chargeback handling (L-12: `available_ucr >= 0` is a constraint today; a negative balance needs a design change), monthly statements and UI.
