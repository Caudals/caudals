## What shipped

- **Migration 107.** better-auth 1.6's two-factor plugin writes `failedVerificationCount` and `lockedUntil` (account lockout: ten wrong codes lock verification for 15 minutes). The production `auth_two_factor` table from migration 003 lacked them, so TOTP enrolment failed for everyone before this package (probe test on the disposable database). The migration adds both columns. The rollback refuses while any account holds lockout state.
- **Sentry, web and workers.** The DSN at `/root/.caudals/secrets/sentry-dsn` becomes a versioned Docker secret (`scripts/sentry-dsn-secret.sh`, `caudals_sentry_dsn_<hash>`). It is mounted as `SENTRY_DSN_FILE` by `deploy-app-stack.sh` on the web app and by `deploy-evals-production.sh` on the worker, scheduler and document services. `SENTRY_RELEASE` is the deployed commit and `SENTRY_SERVICE` names the process. The browser executor has no direct egress by design and does not report.
  - Every event, transaction and breadcrumb passes `lib/observability/sentry-scrub.mjs`, shared by the web app, the workers and the status script. It removes users, IPs, cookies, headers, query strings, bodies, local variables, emails, phone numbers, tokens and connection strings, and keeps UUIDs, dates and codes.
  - Unexpected API failures (503) are captured with their `request_id`. Workers report fatal exits, queue errors, per-task scheduler failures and PDF render failures.
  - `scripts/configure-sentry-runtime.sh` was rewritten for `caudals-app_app` and the worker services (mount or rotate without a redeploy).
  - Test events, with fake personal data that must arrive redacted: `npm run observability:sentry-status -- --send-test-event` (app container) and `services/evals-worker/sentry-test.ts` (worker containers).
- **Platform alerts** (`scripts/evals/health-alerts.sh`, `caudals-evals-health.timer` every ten minutes). New signals:
  - demo failure rate: more than 20 % of demos finished in the last hour failed for service reasons, with at least 3 finished; visitor-side causes are excluded
  - demo queue age and pg-boss engine queue age over 15 minutes
  - webhook failures: outbound deliveries in the last hour, plus `billing.stripe_event` failures once L-12 creates that table
  - credit holds unresolved after 24 hours: a no-op until L-11 creates holds

  Existing checks (DGX, disk at 85 %, memory, Swarm, backups, queue, leases, unknown attempts, providers, budgets, renders) are kept. Behaviour changes:
  - Every alert line links to its runbook section.
  - `CAUDALS_ALERT_DRILL` opens chosen alerts as a drill.
  - Dry runs no longer write state.
  - State is written only after Resend accepts the email, so a failed send retries on the next run.
- **External uptime checks** (`scripts/uptime-checks.sh`, `caudals-uptime.timer` every minute, `scripts/install-uptime-checks.sh`).
  - Checks: landing page, demo API, app sign-in page, auth API and webhook health, through the public internet.
  - A check fails only when two attempts five seconds apart both fail, so an outage alerts within about 90 seconds.
  - Emails: OPEN, then a reminder every six hours, then RESOLVED. Each carries a runbook link.
  - Drill file: `/root/.caudals/uptime-drill`.
- **Webhook health.** `GET /api/evals/v1/health/webhooks` (app host, unauthenticated, cached 15 s) answers 200 or 503 with each check's state and no details. Checks: `database` and `outbound_signing`. L-12 adds its Stripe check to `WEBHOOK_HEALTH_CHECKS` in `lib/observability/webhook-health.ts`.
- **Admin TOTP** (`EVALS_ADMIN_MFA_REQUIRED`, default off).
  - `/workspace/security` (EN/ES, platform kit `AuthFrame`, linked from the account menu as "Account security"): password, then a setup key (grouped, copyable), an `otpauth://` link and ten recovery codes. The person confirms they saved the codes, then enters a first code; better-auth turns two-factor on only after that code verifies. It also covers new recovery codes and turning TOTP off (customers only while enforcement is on).
  - Sign-in accepts a recovery code instead of the app code.
  - With the flag on, `requireIdentity` refuses platform admins, platform operators and workspace operators without TOTP (`MFA_ENROLMENT_REQUIRED`). Pages redirect to `/workspace/security?next=…`, the client API layer redirects too, and `/api/auth/two-factor/disable` is refused for staff. Customers are never required.
  - `requireRecentSignIn` (15 minutes) is the shared check for sensitive actions. Platform changes already use it; billing actions (L-12 top-ups, L-16 grants and adjustments) must call it.
- **Rate limits.** `lib/auth/request-guard.ts` runs in front of `/api/auth/*`. It labels each request with the visitor's proven address: `cf-connecting-ip` is used only when the peer is a Cloudflare range; spoofed headers from other peers are ignored. better-auth's own limits are therefore per visitor, not per Cloudflare edge. Durable PostgreSQL limits:

  | Request | Limit |
  | --- | --- |
  | Sign-in | 20 per visitor and 10 per account per 15 minutes |
  | Two-factor checks | 20 per visitor per 15 minutes |
  | Two-factor management | 10 per visitor per 15 minutes |
  | Reset requests | 5 per visitor per hour |
  | Invitation sign-up | 20 per visitor per hour |

  The sign-in page says "Too many attempts" on a 429. Demo and direct sign-up were already limited.
- **Demo degraded notice.** L-03 already shows it (degraded and capacity notices); unchanged.
- **Runbooks** 11–21 and "Alert drills" in `docs/evals/runbooks.md`: disk and memory, services, queue age, report rendering, demo failures and queue, webhook failures, billing incident, database, uptime, Sentry, admin two-factor (enrolment check, enforcement switch, lost-authenticator reset). Also updated: `docs/TOOLS.md`, `docs/ARCHITECTURE.md`, `docs/VPS_RUNTIME.md`.

## Risks and notes

- Until the arctic install, uptime checks run on the host they watch: they catch app, Traefik, Cloudflare and certificate failures, but not a full atlantic outage.
- The health timer units had disappeared from atlantic (last alert state 2026-10-03), so no platform alerts went out for about nine days. They are reinstalled.
- Browser-side errors are not reported: the client bundle cannot receive the DSN at runtime (no `NEXT_PUBLIC_*` flags). Server-side and worker errors are covered.
- The setup page has no QR code (no new dependency); the setup key and `otpauth://` link work with common authenticator apps.
