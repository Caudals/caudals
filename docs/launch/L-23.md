## What shipped

- **Lint rule `caudals/no-ui-literals`** (`scripts/lint/no-ui-literals.mjs`, registered in `eslint.config.mjs`). It reports JSX text, strings and template literals rendered as children (including both arms of a ternary), visible attributes and props (`aria-label`, `aria-roledescription`, `title`, `placeholder`, `alt`, `label`, `*Label`, `description`, `fallback`, column `headers` arrays…), visible object fields (`label:`, `title:`, `placeholder:`… — tabs, columns, options) and messages passed to `setError`-style setters and toasts. Scope: `components/evals`, `components/demo`, `app/(evaluation)`, the email templates (`lib/email/templates.tsx`, `layout.tsx`), and, because it was already clean, the public site (`components/{landing,public,sectors,contact,call,methodology,sample-report,i18n,legal}`, `app/[locale]`). Not the blog and newsletter (their text is the post's content). Language-neutral text passes: `ALLOWED_TERMS` (brand, product and model names, units, currencies, formats, protocols, identifiers), numbers and punctuation, URLs, e-mails, paths, snake/camel/kebab/CONSTANT identifiers, acronyms, single lower-case codes in setters and fields (`setError("consent")`), and anything inside `<code>`, `<kbd>`, `<pre>`, `<samp>`. A genuine exception takes `// eslint-disable-next-line caudals/no-ui-literals -- reason`; none were needed. Rule tests: `tests/i18n/ui-literals-rule.test.ts` (RuleTester, 20 valid and 13 invalid cases, plus the neutral-text helper).
- **`npm run i18n:check-parity` covers every catalogue** (`scripts/check-i18n-parity.ts`): site JSON (736 keys), app (`lib/evals/messages`, 3,607 keys; until now nothing checked that `es.ts` had every key, and a missing one silently fell back to English), emails (236), PDF/Word labels (133), report summary and fixes (95), readout (124), invoices (7), legal JSON (469; structure and slots), help articles (12 pairs, same front matter), the phrase table (every literal passed to `tr()`/`phrase()`, 131) and, last, the lint rule over its 221 files. It fails on missing or extra keys, blank values, mismatched `{slots}` (one documented exception: the outreach help text shows `{nombre}` to the reader) and Spanish values identical to the English ones unless language-neutral (`SAME_IN_BOTH`: cognates such as *General*, *Plan*, *Total*). About 9 s.
- **Fixed labels are checked too.** `phrases.ts` now types its table (`Phrase`), exports `phrase()` (an identity marker for labels shown later through `tr()`), `hasPhrase()` and `phraseLabels()`. The status-pill table in `primitives.tsx` (98 labels), the operator console's next-step column, the growth table's connection kinds and the evaluation progress steps are typed `Phrase`, so a label without Spanish no longer compiles.
- **Rendered checks.**
  - Emails (`tests/email/templates.test.ts`): every template has the same structure in both languages (block kinds, action and link URLs, steps, facts, footer), and no fixed English wording appears in a Spanish email (subject and text) or Spanish in an English one (whole-word fragments of the other catalogue).
  - PDF and Word (`tests/evals/report-language-parity.test.ts`): the four report fixtures (example EN and ES, preliminary ES, stress EN) rendered in their language carry no wording from the other language's tables and none of the other language's common words.
  - Screens (`e2e/evals/spanish-leaks.ts`): a scanner that reads every visible text node and the attributes people hear and flags English catalogue copy (app, site, phrase table; whole strings and fixed template parts) and, on screens whose content is Spanish, common English words. `e2e/evals/spanish.contract.ts` opens sign-in, direct sign-up, the demo start, the evaluations list, Settings, the help centre, the example, a report (overview, results, methodology), the expert queue and the improvement datasets screen in Spanish at 390 and 1440 px, scans them and saves screenshots; the Spanish tests of the demo (queued, report), direct sign-up, billing (overview, usage, limits, top-up), the run estimate, Home, the evaluations list, the test-set review, intake and the report (own and shared) call the scanner too.
- **Offenders fixed (the sweep).**
  - `components/evals/improvement-datasets.tsx` (ops → Library → Improvement datasets) was entirely English: 108 strings (tabs, forms, options, tables, notices, errors, empty states, the release checklist with English plurals, the follow-up evidence) now use 110 new keys (`imp*`), with stored values (kinds, splits, rights, decisions) shown through the catalogue.
  - Status pills: eight expert-review states had no Spanish and showed English in Spanish (Save conflict, Guideline changed, Submitted, In review, Changes requested, Rejected, Adjudicated, Not required).
  - Stray literals: the outcome bar's screen-reader label ("…, of N."), the readout's `aria-roledescription` ("slides"), the landing carousel's ("carousel", "slide"), the API-key credential's default label, the generated test set's title ("<evaluation> test set", stored in English for Spanish users), the preliminary report's title, the CI-token and webhook name placeholders, the model-route adapter options and price-source placeholder, and the FX-source placeholder.
  - `evaluation-stage.ts` ("Generate the test set", "Add reference material") and the expert tabs ("Open", "All") were already fixed by PR #82 and L-26; they are now guarded by the typed phrases and the lint rule.
  - Rebases: L-19's new destination-name placeholders ("QA team", "Release pipeline") failed the rule and are now catalogue keys; L-19 had already localized the token expiry options, so that part of the sweep was dropped.
  - Terminology: two curated server messages said *plan gratis* where the app says *plan gratuito*.
- **CI and the image build.** `.github/workflows/ci.yml`: the parity step now runs the extended script and the rendered checks (`tests/email/templates.test.ts`, `tests/evals/report-language-parity.test.ts`, `tests/i18n`, `lib/legal`, `lib/evals/help/content.test.ts`), seconds of runner time. The general CI workflow is **manually disabled** on GitHub (checked through the public API: `CI disabled_manually`), so the same gate also runs in the image build (`Dockerfile`, next to the legal/help/methodology gate): `npm run i18n:check-parity && npx vitest run tests/email/templates.test.ts tests/evals/report-language-parity.test.ts tests/i18n`. A literal in a component, a missing translation or a leaking email or PDF now fails the deploy.

## Not done (and why)

- Server error messages: API errors are written in English on the server; the app translates the curated ones (`trServer`), and other server messages still reach a Spanish screen in English. Localizing the API's messages is a separate change (error codes to catalogue keys).
- The plain-text fallback emails used only while `BRANDED_EMAILS_ENABLED` is off (`lib/evals/operations/notifications.ts`, `lib/evals/signup.ts`) are English. The flag is on in production, so no customer receives them; retiring the flag would remove them.
- Internal-only emails (expert-review requests and help requests to the internal address, the ops digest default) stay English by design.

## Risks

- False positives: the allowlist and the code/identifier heuristics keep them low (none in the current tree); a new brand or unit goes into `ALLOWED_TERMS`, a genuine sentence into the catalogue.
- The rule cannot see text assembled in variables away from where it is rendered; the screen scanner and the Spanish contracts catch those on the screens they cover.
- The deploy now fails on a parity problem: a package that adds English strings without Spanish cannot ship until it adds them (intended).
