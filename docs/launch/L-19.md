## What shipped

- **`runs:write` token scope** (`lib/evals/monitoring/tokens.ts`, `customer-api.ts`): offered only with `INTEGRATIONS_V2_ENABLED`; such tokens expire within 90 days (app) and 91 (database check `customer_api_token_write_expiry`). Settings → Developers offers a "CI pipeline: start runs and read their results" token (`runs:write` + `runs:read`) with 1/7/30/90-day expiries and a warning that it spends credits. Token creation and revocation are audited (`api_token.created` with scopes and expiry, `api_token.revoked`); `api_token_created` reports `ci` for these tokens. Workspace deletion now revokes the workspace's tokens and disables its destinations.
- **CI trigger** `POST /api/evals/v1/integrations/runs?orgId=…` (`lib/evals/monitoring/ci-runs.ts`): `{suiteVersionId, targetRevisionId[, evaluationId]}` and an `Idempotency-Key` (8–200 visible characters). Under a transaction advisory lock on the workspace and key, a replay answers 200 with the same run (`replayed: true`), the same key for another body 409 `IDEMPOTENCY_CONFLICT`; otherwise the run is created by the product's own path (`createSelfServiceRunInTransaction`: plan allowance and connection types, euro budgets, L-11 credit admission at the L-10 p90, L-15 monthly and per-run caps) and recorded in `evals.api_run_request` (unique per workspace and key, token provenance, immutable) in the same transaction: each key starts exactly one run under concurrent retries. The run's `created_by` and the audit event `run.started_via_api` name the token; the key is kept only as a hash in the audit. 30 new runs an hour per workspace (replays do not count) on top of L-20's 60 requests a minute per token; collected-answer systems are refused (422). The answer includes the L-10 estimate (credits p50/p90) where the workspace pays with credits and `gate_url`.
- **Release gate** `GET /api/evals/v1/integrations/runs/{runId}/gate?orgId=…` (`runs:read` or `runs:write`): `pass` or `fail` against the threshold set on the schedule that started the run, else on its test set (exact comparison on pass/scored); `unknown` when the run failed, was cancelled or paused (with `credits_exhausted`/`cap_reached`), fewer than 90 % or not every critical question was graded, nothing was scorable, or no threshold is set (`threshold_not_set`); `pending` with `Retry-After: 30` while it runs or is graded. Answers the score, threshold and its source, reasons and report id.
- **Thresholds** (`suite.gate_threshold`, `monitor_schedule.gate_threshold`, 0–100 % with two decimals): Settings → Developers → Release gate lists each approved test set with the test-set and system version IDs a pipeline sends and sets its threshold (`GET /gates`, `PUT /gates/{suiteId}`); a schedule sets its own from its menu or when it is created (`gateThreshold`, keeps the schedule's version). Owners and operators; audited `gate.threshold_saved`.
- **Destinations** (`webhook_endpoint.destination_type`): Slack (only `https://hooks.slack.com/services/…` or Slack GovCloud), Microsoft Teams (Workflows or connector URL; its signed query string kept), email (a verified member's address, or a work address on a member's company domain, `evals.workspace_member_emails`), and the generic signed webhook (unchanged). Every URL passes the webhook egress checks: HTTPS, every DNS answer public (private, loopback, link-local, CGNAT, documentation and mapped ranges refused), the socket pinned to the checked address (DNS rebinding cannot swap it), no redirects, 10 s. The Slack/Teams URL or the address is the credential: kept only in the encrypted envelope (webhook keyring); the list shows a masked hint. Each destination has a message language, "Send test" (a labelled example, five per destination an hour, result shown on the destination, audited `destination.tested`) and delete (`archived_at`, disabled for good, audited `destination.deleted`). Up to 20 destinations per workspace.
- **Regression summaries through the destinations**: `integration-destinations.ts` registers on L-18's `registerSummaryDestination`; in the alert's transaction it queues one `webhook_delivery` per Slack/Teams/email destination and event (with the summary) while the scheduler reads the flag on; the scheduler's webhook tick formats them (`destination-format.ts`: Slack Block Kit with a plain-text fallback, Teams Adaptive Card 1.4, the branded EN/ES `monitor_summary` email, same words from the email catalogue; links to the report and each newly broken answer, or the evaluation) with the same five attempts. The generic webhook's queue and body are unchanged.
- **Developers tab**: destination picker and list, CI tokens, release gate; the API reference documents `runs:write`, the two endpoints with body and fields, 402/409/422, the run-start and token limits, a curl example and a GitHub Actions workflow (start the run with `gh-<sha>-<attempt>` as key, retry safely, poll the gate, fail unless `pass`). Help article "Schedules and regression alerts" (EN/ES) gains "Slack, Teams and email" and "Gate releases from your pipeline".
