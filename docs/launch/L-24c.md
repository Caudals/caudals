## Why sign-up regressed

Every page of the evaluation app imported `t` from `lib/evals/messages/en.ts`, which holds the English catalogue and imports the Spanish one: one 464 KB chunk (~141 KB brotli, ~160 KB gzip) of both languages was on the LCP path of sign-up and sign-in, grown by L-23/L-23b from ~104 KB.

## What shipped

**1. One language, only the keys a page reads (app).**
- `lib/evals/messages/runtime.ts`: `t`, `tv`, `getLocale`, `setLocale` without the catalogues; a store on `globalThis` (the server renders client modules in a different module graph from the layouts). `en.ts` re-exports them and registers both full catalogues when it loads, so server code, tests and the workers call `t(key, locale)` as before; `instrumentation.ts` loads it at start-up as well. 94 client modules (and `phrases.ts`, `api-errors.ts`) import the runtime instead.
- `<EvalsMessages locale messages>` (`components/evals/messages.tsx`) registers a page's messages while it renders, before the components that read them, on the first load and after client-side navigation. The server picks them with `evalsClientMessages(locale, scope)` (`lib/evals/messages/client-messages.ts`, server-only): the evaluation layout sends the frame (`shell`: error, loading, language menu); the signed-in layout sends every key once (client-side navigation inside the app needs nothing more; its pages pick keys from server data such as statuses, roles and reasons, so a static list would risk raw keys); each page outside it sends its own list with `await evalsPageMessages([...])`: sign-in, direct sign-up, sign-up from the link, password reset, invitations (every key when signed in, inside the shell), unsubscribe, two-factor set-up, shared report, fix list.
- The lists are generated from the code: `npm run i18n:evals-client-keys` → `lib/evals/messages/client-keys.ts` (`scripts/i18n/evals-client-keys.ts`: from each page, imports through the UI layer to the `"use client"` boundary and through everything below it; every literal that is a key, props such as `contextKey="invitations"`, and template/concatenation heads such as `` `sheetProblem_${code}` ``).
- Because messages now arrive while the page renders, five modules that built label tables when they loaded (`shell-frame`, `item-actions`, `engine-settings`, `platform-console`, `workspace-data-controls`) build them on use.
- `tests/i18n/evals-client-messages.test.ts` (24 tests, runs in the image build): the generated lists are current; no browser module imports the catalogues or calls `t`/`tv` at module scope; every page outside the signed-in app has an entry and sends it; the payload is one language (sign-up ~2 KB); and each page renders in EN and ES with only the keys it sends without reading another (the shared report on all five tabs of the example report, the fix list loaded). Checked by removing two keys from the list: both reported.
- Unchanged: the L-23 lint rule and parity gate (`npm run i18n:check-parity` passes, 3,995 app keys), the L-23b API-error fallback (`api-errors.ts` and `phrases.ts` stay as they were; they are loaded only where used: not on sign-up or sign-in).

**2. Server-rendered localized 404.** Next 16 renders a `notFound()` thrown while a page renders as an empty error shell (`<html id="__next_error__">`) that the browser fills in; the catch-all `app/[locale]/[...missing]` did exactly that for every miss, and an unknown `[locale]` on the app host did it from the layout. Now:
- `app/[locale]/[...missing]` removed; a URL that matches no page goes to `app/global-not-found.tsx`, which Next renders on the server with status 404: the Paper 404 (`components/public/not-found-view.tsx`, the L-30 view with the free-test link when `DEMO_PUBLIC` is on), in the language of the path (`x-caudals-pathname` from the proxy), else the app's language cookie, the site's, then Accept-Language. Same fonts as the public layout (Geist preloaded; Newsreader with its optical-size axis, not preloaded); `components/document/public-root.tsx` is the public document and providers, shared with `app/[locale]/layout.tsx`.
- `dynamicParams = false` on the landing page: `app.caudals.com/nada` is a miss, not a layout that throws. `/en/sectors/nada` (already `dynamicParams = false`) and `/es/legal/nada` now reach the same 404.
- Pages that check a record (`results/[slug]`, `sector-index/[quarter]`) still call `notFound()`: 404 status, the view appears once the script runs (`app/[locale]/not-found.tsx`, unchanged behaviour).

**3. Smoke test.** `e2e/smoke.spec.ts` checks the current landing: with `DEMO_PUBLIC=true` the hero, header and closing card lead to `/{locale}/demo` (L-04) and the closing card keeps the pilot request (L-30); off, the hero's diagnostic link; both, the call link.

Also: `e2e/public-routes.spec.ts` "404 without JavaScript" (status, no error shell, `<html lang>`, heading, demo and home links; app-host misses with `PLAYWRIGHT_APP_URL`); `e2e/a11y-public.spec.ts` axe on the Spanish 404 and the app-host 404; CI's budgets job also runs when `lib/evals/messages` or `instrumentation.ts` change.
