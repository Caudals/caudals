## Why sign-up regressed

Every page of the evaluation app imported `t` from `lib/evals/messages/en.ts`, which holds the English catalogue and imports the Spanish one: one 464 KB chunk (~141 KB brotli, ~147 KB gzip) of both languages was loaded by sign-up and sign-in, grown by L-23/L-23b from ~104 KB.

## What shipped

**1. One language, only the keys a page reads (app).**
- `lib/evals/messages/runtime.ts`: `t`, `tv`, `getLocale`, `setLocale` without the catalogues, over a store on `globalThis` (the server renders client modules in a different module graph from the layouts). `en.ts` re-exports them and registers both full catalogues when it loads, so server code, tests and the workers call `t(key, locale)` as before; `instrumentation.ts` loads it at start-up too, and Vitest through `test/setup/evals-messages.ts`. 94 client modules, `phrases.ts` and `api-errors.ts` import the runtime instead.

## Why the simulated LCP barely moved

Lighthouse's simulation (Lantern) treats only `h2` as multiplexed (`ConnectionPool.js`: `isH2 = request.protocol === 'h2'`). Cloudflare serves these pages over HTTP/3, so every run models six HTTP/1.1-style connections with a round trip per request; localhost (`next start`, CI) is HTTP/1.1 and gets the same model. The estimate is then bound by how many requests finish before the observed paint (~20 on sign-up: the document, two stylesheets, the manifest, the logo and ~16 script chunks), not by their bytes, and it swings with which of them finish before the paint in the unthrottled trace. Removing the 141 KB catalogue cut 38 % of the app pages' script and some TBT, which real visitors download and parse less of, but not the request count. L-24's 1.8–2.2 s sign-up runs (2026-10-14) are close to the HTTP/2 figures here; the protocol of those runs was not recorded.

Ways to meet the target under that model, not taken here: merge the entry routes' chunks (`experimental.turbopackChunking`: `priorityRoutes` for `/workspace/start`, `/workspace/sign-in`, the landing and the demo, or a higher `minChunkSize`; global and experimental, needs a build to evaluate, so CI's budgets job is the place), and drop `AuthProvider` from the evaluation document (no component calls `useAuth()`; it adds the better-auth chunk and a `get-session` request to every app page, but that request may be what renews the session cookie, so check before removing). CI ceilings unchanged: the after sets do not leave a safe margin under L-24b's (4.5 s, 5.0 s, 300 ms), and the sign-up assertion (LCP < 2.5 s, error) would be flaky in CI under the HTTP/1.1 model (A/B runs to 3.1 s).

## Risks

- A client component on a page outside the signed-in app that reads a key the generated list lacks renders the key; the test renders every such page in both languages and the image build runs it, and the generator must be re-run after changing what those pages show (`npm run i18n:evals-client-keys`; the build says so when the list is stale).
- `t`/`tv` called when a module loads would read an empty store in the browser; the test fails on any such call in client code.
- The signed-in app's messages (~60 KB brotli) are sent with every full page load, and again with `router.refresh()` (a few settings actions), instead of a cached chunk.
- `global-not-found` reads the request, so the 404 renders per request (it was static).
