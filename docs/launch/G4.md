## 1. Lighthouse CI budgets (`lighthouserc.js`)

**The gap.** The mobile sign-up assertion was an error at the 2.5 s budget. lhci asserts its "median run" (the run closest to the median FCP and time to interactive, not the median LCP), and on production that run measured 2.52–3.43 s. The old config fails all five production mobile sets below on that one assertion, so the job would have failed or flaked once CI is re-enabled. The sample report (L-33) was not in the run.

**Now.** Every page and form factor gets the same two levels:

- a **warning at the spec budget** (P-47: LCP 2.5 s, TBT 200 ms, CLS 0.1), shown until it is met; it does not fail the job;
- an **error at a regression ceiling**: the worst median run measured on production + 20 % for LCP or + 50 % for TBT (TBT swings more with the host's load), rounded up to 0.25 s and 50 ms, and never below the budget. Where production meets the budget with room (desktop, CLS everywhere), the ceiling is the budget.

Pages: landing `/en`, demo `/en/demo`, **sample report `/en/sample-report`** (new) and direct sign-up `/workspace/start`. The local server CI starts runs with `EXAMPLE_EVALUATION_ENABLED=true`, because the sample report answers 404 without it (the flag is read per request; `ci.yml` is unchanged). Accessibility score ≥ 0.95 stays an error everywhere.

**Lighthouse version.** All values are **Lighthouse 12.6.1**, the version `@lhci/cli` 0.15.1 pins in `package-lock.json` (Chromium 1243 from Playwright on `atlantic`, simulated throttling, three runs per URL). The config prints a warning when another Lighthouse version runs, since a newer one models HTTP/3 differently (L-24d) and the ceilings must then be re-measured.

## 3. ⌘K: Settings → AI models and Data

- `components/evals/command-palette.tsx` passes `models` and `data` to `settingsTabs` (shared with Settings), so the palette lists exactly what Settings shows the same person:
  - **AI models**: platform admins always (engine settings); owners when `GET /engine/byok` answers for the workspace (BYOK open by `BYOK_ENABLED`/`BYOK_WORKSPACE_IDS`, or a key still connected), the same request Settings makes, sent when the palette opens. Editors and viewers never see it and never send the request. With both BYOK flags off in production, owners do not see it unless a key exists, as in Settings.
  - **Data**: every member while `DATA_CONTROLS_ENABLED` is on (`ShellFeatures.dataControls`, read on the server in `components/evals/shell.tsx`); owners act inside the tab.
- Both entries also match what they do: "retention", "export", "download" / "provider key", "API key", "BYOK" (Spanish: "retención", "exportar", "clave proveedor"…), from two new catalogue keys (`paletteModelsKeywords`, `paletteDataKeywords`, EN/ES).
- UI harness (`e2e/evals/workspace-home.contract.ts`, 2 new tests): an owner with BYOK open and the flag on finds both, "retention" opens Settings → Data and "provider key" Settings → AI models with the tab selected, and the same in Spanish ("Modelos de IA", "retención" → "Datos"); an owner without BYOK and without the flag sees neither; editors and viewers see Data but not AI models and send no `/engine/byok` request; a platform admin sees AI models without that request. The harness router now carries `?data-controls` across navigations like `?owner`.
