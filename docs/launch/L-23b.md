## What shipped

- **Inventory of everything the API can say** (`scripts/i18n/api-errors.ts`, TypeScript parser, no type checker). It walks `lib/evals`, `lib/billing`, `lib/legal`, `lib/analytics`, `lib/workspace`, `lib/public` and `app/api` (552 files) and collects every `new EvalError(code, status, message)` (and its default "This action is not available."), `super(…)` in EvalError subclasses (`PlanLimitError`, `EvidenceError`, `CustomerApiRateLimited`), `EstimateError` details, message tables behind them (`MESSAGES[code]`, `known[1]`, `const [status, message] = TABLE[code] ?? […]`, `...TABLE[code]` spreads, `Object.freeze` tables, imported tables), local and exported helpers that forward a parameter (`fail(message)`, `invalid(code, message)`, `denied()`), `{ error: { code, message } }` bodies of routes outside `api()` (sign-up, unsubscribe, share, runner, token envelopes; shorthand properties too), the sector-pack database messages the API passes through (`RAISE EXCEPTION` in migration 100 with the SQLSTATEs `store.ts`/`refresh.ts` forward), the joined sector-pack item problems, and the sentences of the platform admin's connection and web-search tests and model list. Result: **130 codes, 510 sentences and 33 patterns** (template literals as `…{}…`). Codes taken from the error being mapped (`error.code` with a message table keyed by code) count the table's keys. 16 run-time sites the parser cannot follow (the envelopes forwarding an EvalError, `EstimateError.detail`, the sector-pack database messages, the joined item problems) are listed with a reason in `DYNAMIC_SITES`; a new one fails the gate until it is reviewed.
- **The catalogue** (`lib/evals/messages/api-errors.ts`): `API_MESSAGES_ES` (395 new sentences; the 115 in L-23's `SERVER_ES` in `phrases.ts` still count, read through the new `serverPhrase()`), `API_PATTERNS_ES` (33 patterns; Spanish templates with `{0}`, `{1}`…, numbers in `es-ES` format; functions for the composite ones: a context answer's question plus hint, "row N:" sheet problems with the column codes kept, the pack-file problem list, a provider's own words quoted after our hint, pack version states), `API_CODES` (132 codes with EN and ES: every emitted code plus the client-only `NETWORK_ERROR` and `UNKNOWN`), the generic fallback with the code, the localized support reference and the error page's copy. Terminology follows the app catalogue (Ajustes → …, conjunto de pruebas, ejecución, espacio de trabajo, contrato de encargo del tratamiento, Términos del servicio).
- **What the app shows** (`apiErrorText(code, message)`): English → the server's sentence; Spanish → the sentence's entry, else a pattern, else each sentence of a joined message, else (only for `PROVIDER_UNAVAILABLE`) our hint plus «the provider's own words», else the code's message, else "No se ha podido completar esta acción (código X)…". Never English prose. `Object.hasOwn` lookups (a message such as `constructor` is not a translation).
- **Client wiring.** `components/evals/api.ts`: 4xx and the two 503 configuration errors go through `apiErrorText` (409/429 with a sentence included); a failed `fetch` (offline, DNS) throws `EvalRequestError(0, "NETWORK_ERROR")` with a localized message instead of the browser's "Failed to fetch"; the 5xx "Reference: id." is localized; `evalResponseError(status, body)` for direct-`fetch` uploads (the graded-results upload showed the raw server message). The answer-sheet row problems ("row 3: system_answer_required") use new catalogue keys (`sheetRowProblem`, `sheetRowsToCheck`, `sheetProblem_<code>`). The platform admin's connection and web-search test results go through `apiResultText`/`apiLabelText`. Reason and error codes without a label (`humanize()` fallback, notices, monitoring alert reasons, ingestion reasons, browser captures, narrative drafts, the monthly refresh) show as the code itself in Spanish (`codeText()`), never as English words; the common connection error codes have Spanish labels in the phrase table ("Credenciales no válidas", "Sistema inaccesible"…).
- **A link opened in the browser.** A failing session GET with `Sec-Fetch-Mode: navigate` (a download link, a file in a new tab) answers a small page in the reader's language (cookie, then `Accept-Language`) with the API's status and private headers, instead of raw JSON (`errorPage` in `lib/evals/domain/http.ts`, catalogue loaded on demand so API routes do not carry it; on any failure it falls back to the JSON body). Fetches from the app and integrations keep the JSON contract.
- **Unchanged on purpose.** No API code, status, message or body shape changed. Token APIs for integrators (`/api/evals/v1/integrations/*`, the CI trigger, token estimates) and the private runner keep English codes and messages by contract (documented in `docs/ARCHITECTURE.md`). Legacy `/auth/*` stays English-only (internal). The public demo already shows `demo.errors.<code>` with a localized generic fallback; the new test checks its codes too.
- **The gate.** `apiErrorProblems()` fails on: an emitted code without EN/ES in `API_CODES`, a code or sentence whose Spanish equals the English, a sentence without Spanish, a pattern without Spanish, a Spanish template using a part the English lacks, an unreviewed run-time site, a stale `DYNAMIC_SITES` entry, and a Spanish entry nothing sends any more. It runs in `npm run i18n:check-parity` (new sections "API error messages" and "API errors") and in `tests/i18n/api-errors.test.ts` (also: the extractor finds representative codes, sentences and patterns; `apiErrorText` behaviour; the public demo's 47 codes each have `demo.errors.<code>` in both site catalogues or are listed as generic). Both run in the image build (`Dockerfile`: `npm run i18n:check-parity && npx vitest run … tests/i18n`) and in `ci.yml`, unchanged: a new server sentence without Spanish now fails the deploy.
- **Docs.** `docs/FRONTEND.md` (API errors in the reader's language; the inventory and gate), `docs/ARCHITECTURE.md` (integrator error bodies stay English; the browser error page), `docs/TOOLS.md` (parity command).

## Not done (and why)

- Sector-pack file imports whose problems include validator output (Zod issue text): in Spanish the operator sees the code's message ("Revisa los datos…") instead of the per-item list. Every other pack problem is translated.
- Legacy `/auth/*` and its better-auth messages stay English (internal, English-only by design).
- Demo codes listed as generic in the test (`rate_limited`, `response_*`, `too_many_redirects`, `target_not_json`, `not_ready`) show the demo's localized generic message; specific texts are a copy decision for the public site.
- A model provider's own error text in the platform admin's connection test stays as the provider wrote it, quoted and labelled ("Respuesta del proveedor: «…»").

## Founder actions

- None new. The native-speaker review (L-23, `docs/launch/es-review-checklist.md`) can include a pass over `lib/evals/messages/api-errors.ts`.

## Risks

- The extractor is static: a message assembled somewhere it does not follow becomes an unreviewed run-time site (gate fails) or, if it escapes entirely, shows the code's Spanish message at run time (never English). New message tables keyed by code are picked up when they are object literals.
- Other packages that add server sentences must add Spanish in the same change (intended; the deploy fails otherwise).
- The client bundle of the app gains the Spanish table (~60 KB uncompressed); public pages do not load it.
