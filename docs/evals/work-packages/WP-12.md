# WP-12 — Private runner and CLI integration

Status: production signing key provisioned and a separate-container synthetic runner flow verified; customer-network release acceptance remains open.

The additive migration `040_evals_private_runner.sql` stores pairings, runner identities, candidate jobs and signed submissions under tenant RLS. The workspace can create a short-lived pairing code for a private target, revoke a runner and download a signed offline bundle. The Node CLI in `packages/evals-runner` pairs, checks health, polls, runs a local adapter, uploads resumable signed results and removes local credentials. A repeated identical upload is accepted without a second observation; altered or replayed bytes are rejected. Result provenance says `customer_runner_reported`, and the report names the trust limit of signatures.

The runner API exposes only candidate inputs. It validates signed bundle scope, expiry, project binding and submission ownership; the API never places reference answers or rubrics in the exported bundle. Local configuration and result files are atomically written with owner-only permissions. The CLI guide gives a local adapter contract and installation path.

Evidence: `stage-d-runner.test.ts` covers signature/scope/expiry, `stage-d-runner-cli.test.ts` runs a loopback private-adapter fixture and upload resumption, and `stage-d-runner-db.test.ts` runs pairing/upload/revocation against disposable PostgreSQL. These are isolated fixtures. A real customer-network adapter and a reviewed customer installation/egress policy remain release gates. Multi-turn and attachment cases need a separate capability contract before inclusion in private jobs; the current path accepts text single-turn cases only.

On 2026-09-23, the app received a separate root-managed Ed25519 runner signing key through a versioned Docker secret. The key is not in the app image, browser payload or runner configuration. The deployed app read the mounted key as Ed25519. Using the synthetic evaluation workspace, a temporary owner account created a private target and pairing code through the public app API. The CLI paired from a disposable container on Docker's separate bridge network, checked health, fetched a signed candidate-only bundle, ran a no-side-effect local adapter and uploaded one result. Production recorded a completed run, completed runner job, one submission and an observation labeled `customer_runner_reported`. An exact upload replay returned `duplicate=true`; changing the answer without resigning returned HTTP 404. Revoking the runner denied subsequent health checks. The entitlement was returned to its prior value, the old evaluation target selection restored, and temporary login, runner credentials and local files removed. No customer network, system or credentials were used.

The first replay probe accidentally included the CLI's local `uploaded` marker in the API request and received HTTP 400. It did not indicate a rejected valid replay; the corrected request sent the four fields in `runnerUploadSchema` and passed. This production fixture proves the owned synthetic path, not installation or egress behavior on a customer network. Expired, wrong-project and altered-bundle failures remain covered by isolated protocol fixtures rather than this live run.
