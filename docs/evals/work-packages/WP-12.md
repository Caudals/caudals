# WP-12 — Private runner and CLI integration

Status: implemented locally; live private-network release acceptance remains open.

The additive migration `040_evals_private_runner.sql` stores pairings, runner identities, candidate jobs and signed submissions under tenant RLS. The workspace can create a short-lived pairing code for a private target, revoke a runner and download a signed offline bundle. The Node CLI in `packages/evals-runner` pairs, checks health, polls, runs a local adapter, uploads resumable signed results and removes local credentials. A repeated identical upload is accepted without a second observation; altered or replayed bytes are rejected. Result provenance says `customer_runner_reported`, and the report names the trust limit of signatures.

The runner API exposes only candidate inputs. It validates signed bundle scope, expiry, project binding and submission ownership; the API never places reference answers or rubrics in the exported bundle. Local configuration and result files are atomically written with owner-only permissions. The CLI guide gives a local adapter contract and installation path.

Evidence: `stage-d-runner.test.ts` covers signature/scope/expiry, `stage-d-runner-cli.test.ts` runs a loopback private-adapter fixture and upload resumption, and `stage-d-runner-db.test.ts` runs pairing/upload/revocation against disposable PostgreSQL. These are isolated fixtures. A real customer-network adapter and a production deployment with reviewed key distribution and egress policy remain release gates. Multi-turn and attachment cases need a separate capability contract before inclusion in private jobs; the current path accepts text single-turn cases only.
