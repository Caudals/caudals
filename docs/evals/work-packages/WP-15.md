# WP-15 — Improvement dataset releases

Status: accepted and deployed behind `EVALS_EXPERT_WORK_ENABLED`.

## Delivered contract

Migration `044_evals_improvement_releases.sql` adds tenant-scoped improvement batches and tasks, immutable dataset item revisions and reviews, immutable releases and members, and immutable intervention/follow-up validation records. Every promoted item links to its finding, task, approved expert submission, author, independent reviewer, rights basis, family and split.

Supported release payloads are grounded Q&A, corrected responses, preference pairs with concise rationale, and retrieval content. Hidden chain-of-thought is not requested or exported. A release transaction locks the batch, rechecks independent approval, permitted rights, approved redaction and family contamination, then writes canonical JSONL to private object storage before recording the ready artifact. Retries with an unchanged candidate set return the existing ready release. Artifact download reauthorizes the tenant and verifies the stored byte count and SHA-256; object-store URLs are never returned.

The release includes only eligible approved items; rejected, pending and restricted items remain in the batch's audit trail but cannot become release members. The first JSONL record is a signed manifest followed by ordered canonical item records and a data dictionary. Verification rejects unknown schema majors, wrong keys, modified/truncated/reordered bytes, mismatched item hashes and any family reused across different splits. The manifest carries the Ed25519 public-key fingerprint, content hash, item descriptors, lineage and split counts. Distribute the corresponding public key to the customer through the approved delivery channel; the private key remains server-only.

Follow-up validation records a described customer intervention and evidence reference, then compares existing compatible baseline and follow-up runs without making a target call. It requires at least one matched, scorable held-out case. Training, validation and held-out outcomes are always reported separately. The immutable snapshot states that the observed association does not prove causality and records matched/excluded counts.

## Signing-key rotation and delivery

Provision `EVALS_DATASET_SIGNING_KEY_FILE` as a root-managed Docker secret containing a PKCS#8 Ed25519 private key. Never place it in the image, database, logs or browser payloads. Before rotation, retain and publish the old public key/fingerprint through the controlled customer delivery record so historic artifacts remain verifiable. Mount the new private-key secret, run `npm run evals:release-check-stage-e`, redeploy the immutable image, and use the new fingerprint only for later releases. Rotation does not rewrite or resign an existing release.

Downloads are authenticated app-gateway responses with attachment disposition. Once a customer downloads an exported file it cannot be remotely revoked; operators must use an approved private delivery channel and record the recipient. Deleting or overwriting a released object is not a rollback mechanism.

## Deployment and rollback

Apply migration 044 after 043 through `scripts/evals/migrate.ts` under the migration advisory lock. Run the Stage E release checker before enabling the feature flag. Expected incremental resource use is PostgreSQL rows for expert/dataset provenance plus private object bytes for released JSONL; expert authoring and validation make no model or customer-target calls.

Rollback is feature disable plus forward repair. `db/rollbacks/044_evals_improvement_releases_down.sql` deliberately exits non-zero because released data and intervention evidence are immutable records. Disable `EVALS_EXPERT_WORK_ENABLED`, redeploy the preceding compatible immutable image if needed, retain objects and rows, and add a compatible repair migration. Already downloaded files and published public keys cannot be revoked.
