# WP-10 — Multi-turn and deterministic tools

Status: core runner and operator-gated regression release deployed. The isolated PostgreSQL and synthetic production HTTP release paths pass; the worker/adapter scenarios below remain open.

## Implemented locally

- Frozen scenario graphs support scripted clarification/correction turns, bounded visits, conditional termination, deterministic simulated tool results, final-state predicates and tool traces. A tool schema/transition failure has its own reason code, separate from connector transport errors.
- The runner checks case/run/target/attempt identity and transcript continuity at every turn. Turn, tool, deadline and cumulative output limits stop loops; unavailable provider token usage is recorded as estimated for the local stop, not reported as measured usage.
- The Stage C tests exercise correction, missing-information clarification, tool-error recovery, invalid identity, tool budget, output budget and final-state grading. Comparison checks include frozen policy compatibility.
- A successfully executed but failed or partially failed observation can create a `regression_case` record in pending redaction/validation state; transport errors, passing and unassessed interactions are rejected.
- A platform operator can inspect the failed interaction and source case via `GET /api/evals/v1/regression-cases/{id}`, add a new, source-backed case revision linked to that draft, then call `POST /api/evals/v1/regression-cases/{id}/release` with explicit redaction and validation confirmations. Release requires the named reviewer, locally rechecks the old failed answer against deterministic graders, rejects obvious addresses/credentials and records an audit event. Freezing any suite containing a regression-linked revision requires that exact revision to be released and validated; no endpoint adds it to a suite automatically.

## Release gates still open

- Reviewer confirmation and pattern checks do not replace a full privacy review before using customer interactions.
- Run a bounded multi-turn scenario against a Caudals-controlled production target through the deployed worker and then verify the customer run projection. The disposable PostgreSQL worker/adapter fixture now covers two turns, malformed tool call versus synthetic network failure, tenant isolation and per-turn accounting; production scenario acceptance, fixture reset and incompatible comparison remain open. No synthetic fixture may perform a live side effect.
- Website scenarios need persistent browser context within one case attempt and a verified reset between attempts. Until that exists, the website capability and run gate mark multi-turn cases unsupported rather than scoring a conversation assembled from separate contexts.
- Disclose scripted-user variation and estimated usage in customer-facing methodology before broadening use.

## Per-turn target accounting rollout — 2026-09-25

Migration 057 adds a tenant-scoped `target_invocation_call` record committed before each outbound request. The existing attempt row remains the session reservation. A recorded call retains reported usage; a transport exception or lease recovery leaves that call `unknown`. A scenario failure after recorded tool output does not erase the completed call. Customer run reads count actual calls, with a legacy fallback for attempts predating migration 057. The worker serializes requests-per-minute claims across replicas and uses a fixed reason code for uncertain transport, without storing raw exception text.

The migration was applied under the evaluation migration lock after a fresh root-only database and global-role backup, with general, browser and scheduler dispatch paused and no active target attempts. Its SHA-256 is recorded in production migration history. Commit `dcc9eb3` passed TypeScript, targeted ESLint, the 25-test Stage C suite and a non-owner PostgreSQL fixture exercising single, two-turn, malformed-tool and network-failure worker paths. GitHub Actions CI, Secret Scan, app image build/deploy and evaluation image build/deploy all passed for that commit. App, worker, browser and scheduler run immutable digests from the release; all 16 Swarm services returned to 1/1, and the app, evaluation workspace and Leads health URLs returned HTTP 200. No new production target call was made for this accounting rollout, so the production multi-turn release gate above remains open.
