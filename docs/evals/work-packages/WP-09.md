# WP-09 — Website chatbot connections

Status: local implementation in progress; not release-ready. The browser worker is disabled by default, and no production browser network or real customer widget was changed.

## Implemented locally

- `lib/evals/connectors/browser-executor.ts` discovers a public HTTPS page, proposes a bounded declarative recipe, isolates each invocation in a fresh Playwright context, blocks service workers/downloads, checks navigation/subresources and WebSockets, waits for stable completion, and refuses duplicate new assistant messages. Failed setup closes its context.
- `lib/evals/queue/browser-worker.ts` validates candidate recipes with two fresh-context probes before freezing an immutable recipe and target revision. CAPTCHA, failed capture, drift, and missing recipes enter operator assistance. Submitted model-proposed/operator-authored recipes remain data, never executable scripts.
- A workspace editor must attest authority for the exact endpoint and bounded, non-adversarial activity before a website check or run. Only a platform operator can submit a recipe. This workspace attestation does not replace the written owner permission required for the two real-widget release checks.
- Proposed and frozen recipes must start on the authorized website origin; the submission API and browser worker both reject a recipe that tries to move its probe to another public host.
- Text-stability-only proposals remain in operator assistance and cannot run scored cases. A supported recipe needs a widget busy/ready signal that visibly transitions after submission; an absent signal yields `capture_incomplete` instead of a potentially partial graded response.
- Migration 039 records candidates, revisions, encrypted-session references and connection state; the browser service uses an explicit tenant allowlist, dedicated database grants and a browser-session-only keyring. Local fixtures cover iframe, open shadow DOM, streaming/delay, duplicate DOM messages, reset isolation, selector drift and a private WebSocket handshake.
- Run the isolated browser fixtures with `npx playwright test --config=e2e/evals/browser-fixture.config.ts`; they need no production site or Next server.

## Release gates still open

- The external `evals_browser_egress` network is referenced by Compose but no enforceable firewall/proxy policy has been provisioned or tested. Application request interception is not a substitute for container-level egress isolation or DNS-rebinding protection.
- No owner-authorized real widget has yet passed discovery, probe, run and reset; the specification requires two. Never probe a named third-party system without written owner authorization and agreed prompts/limits.
- Login-session capture/expiry UX and redacted screenshot/trace artifact capture are not complete. The schema and secret-read path alone do not satisfy that deliverable.
- Each authorized real-widget check still needs its own validated completion selector; generic text stability is intentionally refused for scored runs.

## Public candidate shortlist (not authorization)

- [Tidio Lyro playground](https://www.tidio.com/ai-agent/playground/) explicitly offers demonstrative chatbot questions and a reset control. Its [terms](https://www.tidio.com/terms/) apply to visitors and prohibit unauthorized crawling/scraping; obtain written permission from Tidio for the precise automated discovery/probe/run/reset scope before testing it.
- [Botpress interactive demo catalogue](https://botpress.com/botpress-demos) advertises conversational AI demos. Confirm a specific active widget and obtain written permission from its owner before automated checks; a public demo listing is not permission.

Record owner, permitted URL/origins, test prompts, rate/concurrency cap, duration and evidence retention for each of the two real-widget checks. Neither candidate has been probed.

Keep `EVALS_BROWSER_ENABLED=false` until the network policy, real-widget evidence, login handling and redacted artifact checks are reviewed. Do not enable broad customer access at this gate.
