# WP-09 — Website chatbot connections

Status: deployed for the synthetic workspace. Login sessions, redacted screenshot capture and multi-turn website support within one attempt are implemented. Customer widgets still need per-site recipes and remain outside the allowlist.

## Implemented locally

- `lib/evals/connectors/browser-executor.ts` discovers a public HTTPS page, proposes a bounded declarative recipe, isolates each invocation in a fresh Playwright context, blocks service workers/downloads, checks navigation/subresources and WebSockets, waits for stable completion, and refuses duplicate new assistant messages. Failed setup closes its context.
- `lib/evals/queue/browser-worker.ts` validates candidate recipes with two fresh-context probes before freezing an immutable recipe and target revision. CAPTCHA, failed capture, drift, and missing recipes enter operator assistance. Submitted model-proposed/operator-authored recipes remain data, never executable scripts.
- A workspace editor must attest authority for the exact endpoint and bounded, non-adversarial activity before a website check or run. Only a platform operator can submit a recipe.
- Proposed and frozen recipes must start on the authorized website origin; the submission API and browser worker both reject a recipe that tries to move its probe to another public host.
- Text-stability-only proposals remain in operator assistance and cannot run scored cases. A supported recipe needs a widget busy/ready signal that visibly transitions after submission; an absent signal yields `capture_incomplete` instead of a potentially partial graded response.
- Migration 039 records candidates, revisions, encrypted-session references and connection state; the browser service uses an explicit tenant allowlist, dedicated database grants and a browser-session-only keyring. Local fixtures cover iframe, open shadow DOM, streaming/delay, duplicate DOM messages, reset isolation, selector drift and a private WebSocket handshake.
- Before loading an encrypted login state, the browser executor now rejects cookies for a domain other than the attested website host and local storage for any other origin. This is a fail-closed session boundary; cross-origin login flows need an explicit reviewed capability contract before support.
- Run the isolated browser fixtures with `npx playwright test --config=e2e/evals/browser-fixture.config.ts`; they need no production site or Next server. On 2026-09-23, six tests passed, including a tiny synthetic HTTPS chatbot served from loopback. The connector discovered its URL, performed two separate-context reset probes, waited for the streaming completion signal and captured the final answer. The test's destination checker admits only that fixture origin; production URL policy is unchanged.

## Release gates still open

- The production browser has only the internal overlay network. Its separate HTTPS CONNECT proxy resolves and pins public IPs. A live CHECK from the browser container rejected metadata, DGX-private and loopback destinations with HTTP 403 while accepting the Caudals public fixture host with 204. Continue testing redirect, subresource, WebSocket and DNS-rebinding behavior as part of every browser release.
- Verification uses the existing Caudals mockup chatbot. Testing with external/third-party chatbots has been removed from the specification per founder direction; the mockup fixture is sufficient. Its production URL, two reset probes, frozen recipe, queued invocation and scoring are verified below. Existing iframe, shadow DOM, duplicate, reset, selector drift and private WebSocket fixtures cover isolated behavior.
- Closed 2026-09-25: login-session capture/expiry/revocation and masked screenshot capture shipped (see production closure below). Full Playwright trace capture is not stored, because traces can contain unmasked page content.
- Each deployed widget still needs its own validated completion selector; generic text stability is intentionally refused for scored runs.
- Closed 2026-09-25 (see below): one isolated browser context now persists across the turns of an attempt and is reset between attempts. Previously, multi-turn website cases were explicitly unsupported. The former capability report advertised support even though each invocation opened a fresh context; the run gate now refuses these cases, including previously checked recipes.

## Production fixture acceptance — 2026-09-24

The Caudals-controlled `https://app.caudals.com/evaluation-entry/fixture` was attested by the synthetic workspace. Automatic discovery correctly required operator help because text stability alone did not prove completion. An operator recipe with a busy selector passed two fresh-context reset probes and froze target revision `a1e57088-aea5-4833-a24f-8eb4d63bb1e4`.

The first queued run exposed missing browser-role access to the target invocation ledger; migration 048 granted the minimal SELECT, INSERT and UPDATE privileges. A canceled stuck run then exposed an inconsistent run projection; commit `0876fc2` settles canceled case units and the run, with a PostgreSQL integration regression. The next run exposed missing UPDATE permission for `target_attempt.dispatched_at`; migration 049 fixed it and was checked on a disposable PostgreSQL instance and in production.

Run `672072a6-bfb7-4151-8706-1f7b10150e06` completed with one succeeded case unit, one completed attempt, one observation and a `recorded` target invocation ledger entry with a dispatch timestamp. The authenticated scoring endpoint created one assessment. The mock chatbot echoed the question, so deterministic grading correctly marked the policy calculation case as failed; execution success does not imply model-answer correctness. After each probe, the temporary account password, operator role and sessions were removed; the final database check found zero sessions and roles and an unverified email.

## Production closure — 2026-09-25 (UTC)

- Migration 062 and `repositories/browser-sessions.ts` add encrypted website login sessions with a maximum lifetime of 168 hours. They are stored with the browser-session keyring and can be listed and revoked, and the workspace UI manages them. When discovery needs an operator, the browser worker stores a masked viewport JPEG as a `browser_capture`, readable through `/browser-captures/:id` and purged by the lifecycle job.
- Multi-turn websites: the worker keeps one browser context per target attempt, rejects identity or transcript mismatches between turns and closes the context when the attempt ends. A fresh context is used for every attempt. Recipe validation now also sends a follow-up in the same context and sets `multi_turn_verified` only when both turns capture complete, distinct, non-duplicated replies. Only then does the capability report advertise `multi_turn`; recipes probed before this change stay single-turn until re-probed.
- Fixed a completion race in `waitForCompletion`. The busy signal was read after the text, so a widget that swapped in the final answer and cleared its busy state between the two reads could yield the partial text ("Partial" in the fixture, failing about one run in three). The signal is now read first. The six browser fixture tests then passed on six consecutive runs.
