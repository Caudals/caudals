# WP-14 — Expert assignments and quality review

Status: accepted and deployed behind `EVALS_EXPERT_WORK_ENABLED`.

## Delivered contract

Migration `043_evals_expert_work.sql` adds platform-managed expert profiles, immutable guideline revisions, tenant-scoped assignments and redacted evidence snapshots, conflict declarations, append-only submission revisions, independent quality reviews and manual payment records. The `/review` workbench derives tenant authority from the assigned expert profile rather than a caller-supplied workspace. Operator APIs still require a platform role and workspace-manage authority.

Experts receive only the redacted evidence snapshot and guideline attached to their assignment. Independent reviewers also receive the submission answer, rationale and source anchors with author and raw source identities removed. Blind review hides model, author and peer identities until an operator explicitly ends the configured phase. Raw RLS checks limit direct assignment/evidence reads to the assigned profile and hide payment records even when an expert transaction carries the assignment's tenant context. Saves use optimistic versions: a stale save is retained as a competing immutable revision, the current pointer is not silently overwritten, and the assignment enters conflict resolution. Submitted work is locked. A reviewer cannot approve their own work or act after disclosing a conflict; critical approval requires a distinct submitted review assignment. Superseded guidelines flag unfinished work instead of rewriting it.

Quality reporting includes reviewed and gold-item counts. It does not rank an expert until the configured minimum sample is met. Payment records are administrative notes for manual invoice handling: this package does not transfer money, call Stripe, calculate tax, or promise automated freelancer payouts.

## Operations and release gate

Stage E stays unavailable unless `EVALS_EXPERT_WORK_ENABLED=true`. Enable it only after migrations 043–044, the dataset signing key, the runtime-role check and the immutable-trigger check all pass through `npm run evals:release-check-stage-e`. Keep customer registration invite-only.

The runtime connection inherits `evals_runtime`, which is `NOLOGIN NOSUPERUSER NOBYPASSRLS` and owns no `evals` objects. Every login member is also checked for `SUPERUSER`, `BYPASSRLS` and ownership. Migration execution uses the separate migration owner under the existing advisory lock. The Stage E release checker emits only migration identifiers and aggregate configuration counts; it does not print key material, expert identities or customer content.

Rollback is feature disable plus forward repair. `db/rollbacks/043_evals_expert_work_down.sql` deliberately exits non-zero because attributed expert, review and payment history must not be erased. Disable `EVALS_EXPERT_WORK_ENABLED`, redeploy a compatible immutable image, preserve all records, and ship an additive repair migration.

## Verification evidence

- `stage-e-experts.test.ts`: strict contracts, blind projections and sample-aware quality metrics.
- `stage-e-expert-db.test.ts`: cross-tenant and assignment isolation, append-only conflict preservation, self-review rejection, critical independent review, guideline invalidation and payment visibility against PostgreSQL.
- `e2e/evals/ui.contract.ts`: redacted workbench, keyboard access, stale-save recovery and operator conflict/payment workflow.
- `stage-e-release.test.ts`: release-gate failures for incomplete migrations, privileged/owning runtime roles, missing immutable triggers, disabled feature flag and non-Ed25519 keys.

Known live limitations: contracts and payments remain operator-managed; there is no automated payout or open expert marketplace. Production assignment acceptance must use synthetic redacted evidence only and must not expose a named customer's evaluation data.
