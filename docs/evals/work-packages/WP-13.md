# WP-13 — Scheduled monitoring and integrations

Status: implemented locally for invite-only workspaces; live deployment acceptance remains open.

Migration `041_evals_monitoring.sql` adds tenant-scoped schedules, unique slot dispatches, alerts, webhooks, scoped API tokens and explicit CRM drafts. A schedule pins an approved suite and target revision; a suite expansion requires a versioned update. Daily, weekly and monthly slots use an IANA timezone. A DST gap is skipped, a repeated time uses its first occurrence, and a date absent from a shorter month is skipped. After downtime, one latest missed slot is claimed and the skipped count is retained. The worker records budget, source-age, overlap and changed-policy skip reasons. Pausing remains available when an evaluation loses readiness.

Monitoring outcomes grade terminal scheduled runs, compare with the latest completed scheduled baseline, and mark failed runs `unknown`, inadequate coverage or incompatible plans `inconclusive`, and only assessed comparable case regressions `regression`. In-app notifications and a read-only CI status API expose the outcome. Webhooks send compact IDs/status, use a pinned public HTTPS destination, sign the delivery ID, timestamp and exact body, reject redirects, and retry at most five times without rerunning the evaluation. Receivers must retain delivery IDs for replay rejection. Customer tokens are hash-only, scoped, expiring and revocable. An operator may explicitly create a private reviewed-report CRM handoff draft; no Leads write or automatic outreach occurs.

The workspace settings page creates and pauses schedules, shows skip and alert reasons, and manages webhooks and tokens. The internal APIs are `/api/evals/v1/schedules`, `/alerts`, `/webhooks`, `/tokens` and `/crm-handoff-drafts`. Bearer clients read `/api/evals/v1/integrations/{runs|reports|schedules}` and `/integrations/ci/{scheduleId}` with `orgId` and the corresponding scope.

Evidence: calendar, signature, token, alert and CRM unit tests plus `stage-d-monitor-db.test.ts` against disposable PostgreSQL cover catch-up uniqueness, budget, source freshness, overlap, token revocation, delivery deduplication/retry limit and inconclusive alerts. Live webhook receiver behavior, real scheduled execution with funded limits, UI accessibility and restart under two worker replicas still need release verification. No production schedule worker is enabled by this change.
