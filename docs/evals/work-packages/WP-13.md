# WP-13 — Scheduled monitoring and integrations

Status: isolated scheduler deployed and synthetic production schedule/delivery verified; broad customer release remains gated.

Migration `041_evals_monitoring.sql` adds tenant-scoped schedules, unique slot dispatches, alerts, webhooks, scoped API tokens and explicit CRM drafts; additive migration `042_evals_monitor_schedule_reasons.sql` records the current schedule pause reason without changing the applied WP-13 migration. A schedule pins an approved suite and target revision; a suite expansion requires a versioned update. Daily, weekly and monthly slots use an IANA timezone. A DST gap is skipped, a repeated time uses its first occurrence, and a date absent from a shorter month is skipped. After downtime, one latest missed slot is claimed and the skipped count is retained. The worker records budget, source-age, overlap and changed-policy skip reasons. Pausing remains available when an evaluation loses readiness.

Monitoring outcomes grade terminal scheduled runs, compare with the latest completed scheduled baseline, and mark failed runs `unknown`, inadequate coverage or incompatible plans `inconclusive`, and only assessed comparable case regressions `regression`. In-app notifications and a read-only CI status API expose the outcome. Webhooks send compact IDs/status, use a pinned public HTTPS destination, sign the delivery ID, timestamp and exact body, reject redirects, and retry at most five times without rerunning the evaluation. Receivers must retain delivery IDs for replay rejection. Customer tokens are hash-only, scoped, expiring and revocable. An operator may explicitly create a private reviewed-report CRM handoff draft; no Leads write or automatic outreach occurs.

The workspace settings page creates and pauses schedules, shows skip and alert reasons, and manages webhooks and tokens. The internal APIs are `/api/evals/v1/schedules`, `/alerts`, `/webhooks`, `/tokens` and `/crm-handoff-drafts`. Bearer clients read `/api/evals/v1/integrations/{runs|reports|schedules}` and `/integrations/ci/{scheduleId}` with `orgId` and the corresponding scope.

Evidence: calendar, signature, token, alert and CRM unit tests plus `stage-d-monitor-db.test.ts` against disposable PostgreSQL cover catch-up uniqueness, budget, source freshness, overlap, token revocation, delivery deduplication/retry limit and inconclusive alerts.

The production scheduler now runs as a separate 1/1 service with a non-owner,
NOBYPASSRLS `evals_scheduler` login that inherits the tenant runtime grants. It
has an explicit synthetic-workspace allowlist, its own database credential and
webhook keyring, a one-minute tick and a health heartbeat. The ordinary
inference worker no longer runs schedules. The app has the matching webhook
keyring for endpoint creation and rotation.

On 2026-09-23, a Caudals-owned synthetic schedule created three bounded runs
through the production queue and target worker. All completed with recorded
target invocation usage. The first monitoring result was `inconclusive`
(`no_baseline`); the second and third were compatible `pass` comparisons. The
last result queued one signed webhook and the scheduler delivered it once to a
Caudals-owned HTTPS fixture, receiving HTTP 204. The fixture validates bounded
event shape, delivery-header syntax and timestamp; it does not independently
verify the HMAC. The protocol unit test checks exact-byte HMAC binding and
replay rejection. The schedule was paused, endpoint disabled, synthetic
`can_schedule` entitlement reset, and temporary login revoked. No customer
destination was contacted.

Remaining release checks: a receiving system that independently verifies the
HMAC, UI accessibility, worker restart and contention under two scheduler
replicas, and customer rollout policy. Customer workspaces remain outside the
service allowlist.
