# Evaluation platform specification closure plan

Snapshot: 2026-09-25. Source of truth: `docs/product-specs/evals-platform-implementation-spec.md` (especially §§17, 20 and 22), the sixteen `docs/evals/work-packages/WP-*.md` handoffs, and the deployed synthetic acceptance records in those handoffs. This is a gap register, not a claim that a package is complete. Recheck production state and the deployed Git commit before changing any status.

## Closure rule

A package closes only when its deliverables and acceptance criteria have reproducible code/test evidence, its applicable production path has been exercised on the deployed commit, security and recovery gates pass, and its handoff records the evidence and remaining limits accurately. Synthetic evidence may prove system behavior but cannot substitute for a specified authorized real integration or customer-network check. No customer workspace enters a dispatch allowlist until its owner authorization, consent, destination policy and the global release gates pass. Keep a failing or uncertain attempt as evidence; do not rewrite it to make a gate green.

Global gates shared by multiple packages:

1. **Recovery and capacity:** reach the spec's 30% free-disk target with measured run/build headroom; verify CPU, memory, PID, temporary-file and log bounds. Produce an encrypted off-host database/object/role backup, restore the full identity and object system in isolation, replay a separately retained post-snapshot revocation/deletion ledger before access, and prove the documented RPO/RTO. The 2026-09-23 same-host rehearsal is partial. Current VPS disk use is about 88–89%, above the 70% target.
2. **Deployment integrity:** apply every additive migration under the lock with checksum verification, preserve compatible worker rollout, deploy immutable image digests, wait for every Swarm service to converge, run public/app/Leads health and a bounded evaluation smoke. Verify CI, Secret Scan, app build/deploy and evaluation image build/deploy on the final `main` commit. The uncommitted WP-10 per-turn usage repair introduces migration 057 and needs a coordinated migration/worker rollout.
3. **External release evidence:** obtain written authority for two real website widgets; an approved customer-controlled private runner/API test environment and network policy; an independently HMAC-verifying receiver; an approved off-host backup destination and key custody; and approved bounded commercial-provider credentials where the spec requires a real-provider probe. Do not synthesize these approvals or probe third-party systems without them.
4. **Security and lifecycle:** verify tenant isolation and least-privilege service roles after migration, destination egress policy, secret/PII redaction, source and result provenance, retention execution, audit/recovery controls, share revocation and no unintended external side effects. Complete operational observability, queue/lease/backup alerts and runbooks under §17.6.

## Stage and end-to-end closure order

1. **Stage A (WP-00–02):** refresh and accept foundation handoffs, run final role/RLS/storage fixtures and production auth/route smoke. Keep immutable evidence and existing site/CRM behavior intact.
2. **Stage B (WP-03–08):** finish the WP-10 accounting defect first because it affects Stage B spend reporting; coordinate migration and worker deployment. Then close provider/target, generation/scoring/report E2E and the global recovery/capacity/operational release gate. Customer dispatch remains off until it passes.
3. **Stage C (WP-09–11):** finish browser session/artifacts and multi-turn worker behavior, then the full invited customer journey and two authorized widgets. Validate desktop/mobile and assistance/recovery paths with the deployed image.
4. **Stage D (WP-12–13):** complete authorized private network install, independent webhook receiver and scheduler crash recovery before customer rollout.
5. **Stage E (WP-14–15):** exercise the already deployed expert and dataset workflows with synthetic data end-to-end, then prepare governed real expert access and private delivery.

The ten required §22.2 scenarios are separate exit checks. Current status is: (1) happy path **partial** (synthetic pieces, no single reviewed full journey); (2) XLSX correction **fixture only**; (3) website drift **fixture only**; (4) budget race **integration fixture**; (5) crash boundary **integration fixture**, per-turn ambiguity open; (6) evidence dispute **unit/integration only**; (7) tenant attack **RLS/API fixtures**, final deployed adversarial check due; (8) tool workflow **runner fixtures**, actual worker path due; (9) iteration **synthetic comparable rerun passed**, edited-scope overlap E2E due; (10) deletion/restore **partial same-host rehearsal**, full off-host replay gate open. For each, retain run IDs, version hashes, test result, deployed digest and observed outcome in the responsible WP handoff; do not use a test that only mirrors implementation as the sole proof.

## Finish line

Close every WP handoff with an explicit accepted status and evidence on the final `main` SHA; update the draft spec's stale implementation status; pass required contract, DB, connector, security, recovery, E2E, visual and operational layers; verify green GitHub Actions builds and a converged production deployment; record unresolved external limitations honestly. If a written authorization, customer environment, backup destination or provider credential is unavailable, continue independent closure work, but leave the associated package and full-product release gate open.
